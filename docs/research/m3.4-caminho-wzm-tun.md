## 2. Item 1 — parser do TUN corrigido (IPv6 ≠ pacote inválido)

Novo `IpPacketParser` (Kotlin puro): antes de descartar, registra **tamanho total, versão, cabeçalho, protocolo,
endereços (IPv4 e IPv6), portas TCP/UDP, flags TCP, tamanho declarado pelo cabeçalho IP e tamanho de payload**.

| Situação | Antes | Agora |
|---|---|---|
| IPv6 válido (48 B, 76 B, TCP/UDP/ICMPv6, com extensões) | `PACOTE_INVALIDO` | `IPv6 UDP [fe80::1]:5353 -> [::ffff:10.111.222.1]:53 …` + descarte com `motivo=IPV6_SEM_ATENDIMENTO` |
| IPv4 com IHL inconsistente | `PACOTE_INVALIDO` | `motivo=IPV4_CABECALHO_INCONSISTENTE` |
| total length < cabeçalho (payload menor que o header) | `PACOTE_INVALIDO` | `motivo=TAMANHO_DECLARADO_MENOR_QUE_CABECALHO` |
| total length > bytes lidos | `PACOTE_INVALIDO` | `motivo=TAMANHO_DECLARADO_MAIOR_QUE_LIDO` |
| cabeçalho TCP/UDP não cabe | `PACOTE_INVALIDO` | `motivo=TRANSPORTE_CABECALHO_CURTO` |
| IPv6 com menos de 40 B | `PACOTE_INVALIDO` | `motivo=IPV6_CABECALHO_CURTO` |
| < 20 B | `PACOTE_INVALIDO` | `motivo=CURTO_DEMAIS` |
| nibble ≠ 4/6 | `PACOTE_INVALIDO` | `motivo=VERSAO_DESCONHECIDA` |

Quando (e **somente** quando) o pacote é realmente inválido, o log traz uma prévia hexadecimal **limitada a 32
bytes**, com nota explícita de que se trata de cabeçalho/prefixo desconhecido:

```
[TUN] pacote descartado: motivo=VERSAO_DESCONHECIDA (lido=76 B nibble=0x1 hex[<=32]={11 11 11 …}) — o primeiro nibble não é 4 (IPv4) nem 6 (IPv6)
```

Nenhum pacote **válido** tem bytes registrados: só metadados. Sem corpos HTTP, cookies, tokens ou credenciais.

### Contadores novos (nomes exatos usados no log, no card e no `.txt`)

`tunPacketsTotal`, `tunIpv4Packets`, `tunIpv6Packets`, `tunTcpPackets`, `tunUdpPackets`, `tunIcmpPackets`,
`tunInvalidPackets`, `tunIpv4ToCdnTarget`, `tunIpv6ToCdnTarget`, `tunToRedirect`, `tunBounces`, `tunDiscards`,
`tunTcpSyn`, `tunTcpSynToRedirect`, `tunTcpSynOther`, `tunUdpDns53`, `tunUdpDnsNoVirtualDns`, `tunDotFlows`,
`tunDohCandidates`, `tunTcp443Externo`, `tunUidVerifiedFlows`.

## 3. Item 2 — o tráfego do WZM realmente entra na VPN?

A aceitação do `addAllowedApplication` **não** prova autoria de pacote. O launcher agora coleta três camadas:

1. **Cabeçalho de sessão** — pacote/versão/UID alvo, se o per-app foi aceito e com que provedor de rede veio
   (`[DIAG] sessão=#N`, `[DIAG] pacote alvo=… uid=…`, `[DIAG] rede VPN: interface=… rotas=[…] dns=[…]`).
2. **Dono do fluxo** — para cada SYN observado no TUN, consulta `ConnectivityManager.getConnectionOwnerUid`
   (API 29+, pública, sem root) nas duas orientações. Se resolver, o log diz `dono=uid=10692 (com.activision.…)` e
   o contador `tunUidVerifiedFlows` sobe; se não, diz `NAO_RESOLVIDO` — **nunca** se presume autoria.
3. **Quadro de evidências** (§6), que resume o encadeamento:
   `VPN criada → app na allow-list → pacote no TUN → IPv4/IPv6 válido → destino → protocolo/porta → (CDNI) → listener`.

Linhas de encadeamento emitidas:

```
[DIAG] estado do roteador: PARADO -> VPN_STARTING (pedido de túnel enviado ao sistema (per-app: …))
[DIAG] endereço do túnel 10.111.222.1 confirmado nas interfaces após 412 ms (tun0 pronto)
[DIAG] estado do roteador: VPN_READY -> LOCAL_SERVER_STARTING (…retry limitado (8 tentativas))
[CDNI] HTTPS local escutando em 10.111.222.1:443 (papel=TUNEL_PRIMARIO)
[DIAG] estado do roteador: LOCAL_SERVER_READY -> ROUTER_READY (listener no endereço do túnel ativo)
```

## 4. Item 3 — DNS: medir, não supor

Cada consulta DNS vista no túnel sai completa (nome, tipo, origem→destino, servidor classificado, resposta e
"CDNI: sim/não"):

```
[DNS] consulta: prod.cdni.callofduty.com (tipo 1) 10.111.222.1:53000 -> 10.111.222.2:53 servidor=virtual-do-tunel -> RESPOSTA A=10.111.222.1 [DNS CDNI recebido e interceptado: sim] (60 B)
[DNS] consulta: dns.adguard.com (tipo 28) 10.111.222.1:53000 -> 10.111.222.2:53 servidor=virtual-do-tunel [DNS CDNI recebido e interceptado: não]
[DNS] dns.adguard.com (tipo 28) … servidor=virtual-do-tunel -> encaminhado ao DNS real (não é host CDNI; resposta 76 B)
```

Separações medidas: `tunUdpDns53` (porta 53 no túnel), `tunUdpDnsNoVirtualDns` (**chegou em `10.111.222.2`?**),
`dnsForwarded` (não era CDNI), `dnsIntercepted` (era CDNI). O quanto o WZM usa DoT/DoH/**** é **identificado**, nunca
descriptografado: `tunDotFlows` (porta 853), `tunDohCandidates` (UDP :443 = QUIC/DoH candidato, `HYPOTHESIS`),
`tunTcp443Externo` (TCP :443 para IP externo, só destino/porta/protocolo).

DNS privado do sistema é lido (best-effort) para **evidência do que está configurado**:

```
[DIAG] DNS privado (DoT) configurado: VERIFIED (Settings.Global private_dns_mode=hostname specifier=dns.adguard.com) — efeito sobre o WZM: HYPOTHESIS (…)
```

Se a leitura não for possível, sai como `UNKNOWN` — nunca como conclusão.

## 5. Item 4 — ciclo de vida correto (o bug do EADDRNOTAVAIL)

Ordem implementada (estado explícito, sem retry cego):

```
VPN_STARTING → VPN_READY → LOCAL_SERVER_STARTING → LOCAL_SERVER_READY → ROUTER_READY
```

1. `startRouter()` sobe **primeiro a VPN** (o antigo fluxo iniciava o servidor HTTPS antes — origem do EADDRNOTAVAIL);
2. o serviço espera o endereço do túnel de forma **limitada** (5 s, poll de 250 ms) e loga o resultado;
3. só então o controlador inicia o listener, com **retry limitado** (8 tentativas de 350 ms) e **apenas** quando o
   erro é EADDRNOTAVAIL — qualquer outro erro de bind encerra o loop na hora;
4. `ROUTER_READY` **só** é declarado com o listener `10.111.222.1:443` ativo; se ele for impossível, a fase para em
   `LOCAL_SERVER_READY`, a limitação fica registrada (`LIMITAÇÃO DOCUMENTADA`) e o log diz explicitamente
   "O estado do roteador NÃO avança para ROUTER_READY".

O listener de loopback continua existindo **separado** (`papel=LOOPBACK_DIAGNOSTICO`), como caminho de diagnóstico —
o roteador não é declarado pronto por causa dele. A fase aparece na tela principal ("Fase — …") e no `[DIAG]`.

## 8. Item 8 — critérios de sucesso e como fechar cada caso

Depois de rodar o APK instrumentado no device, **uma** destas conclusões fica sustentada por log:

**Caso A — o WZM gera tráfego CDNI (esperado).** Encadeamento completo:
`[DIAG] pacote alvo=… uid=10692` → `[DNS] consulta: prod.cdni.callofduty.com … interceptado: sim` →
`[CDNI] TCP SYN … -> 10.111.222.1:443 (bounce #N)` → `[CDNI] tentativa de conexão em 10.111.222.1:443 (via túnel): dono=uid=10692`.
Contadores: `dnsIntercepted ≥ 1`, `tunTcpSynToRedirect ≥ 1`, `tunToRedirect ≥ 1`, `tunBounces ≥ 1`, `tunUidVerifiedFlows ≥ 1`.

**Caso B — o WZM não gera tráfego relevante.** Evidências: `[DIAG] nenhum pacote no TUN…` (ou pacotes só de ICMPv6/DoT
de sistema), `tunUidVerifiedFlows=0`, `tunTcpSyn=0` **com** `[DIAG] pacote alvo=… instalado=sim` e a fase
`ROUTER_READY`. Só assim se conclui "não houve tentativa" — nunca por ausência silenciosa.

**Caso C — o WZM usa outro formato/caminho.** Identificado por contador e documentado como `VERIFIED` (o fluxo
existe) + `HYPOTHESIS`/`PROBABLE` (o que ele significa): IPv6 (`tunIpv6Packets>0`), DoT (`tunDotFlows>0`),
QUIC/DoH (`tunDohCandidates>0`), TCP :443 para IP externo (`tunTcp443Externo>0`), cache/IP fixo
(`tunPacketsTotal=0` com app ativo e rede funcionando).

**Passo a passo para o teste no device:** `docs/launcher.md` §5.2 (tela VER LOGS → SALVAR .TXT) e o protocolo de
reprodução em [`m3.3-diferenca-entre-os-testes.md`](m3.3-diferenca-entre-os-testes.md) §7 — o que muda é que agora o
`.txt` traz o quadro de evidências pronto.

* TLS/certificados/trust store/pinning/bypass: **nada** foi alterado (e nada será sem decisão explícita).

* Nenhum descriptografia de DoT/DoH, nenhuma interceptação de credenciais, nenhum bypass de segurança.
* Nenhum root, patch de APK, Frida ou alteração do app do jogo; o server segue **apenas** loopback/túnel.

## 10. Próximo passo depois desta etapa

Com tráfego CDNI chegando ao roteador (Caso A), a próxima camada é a que já está mapeada e **bloqueada por design**:
confiança TLS do cliente (M3.2). Só depois de o quadro de evidências mostrar o SYN no listener é que faz sentido
discutir a cadeia de confiança — e mesmo aí sem bypass: a decisão do M3.2 continua valendo.
