# M4.8 — Sequência Pre-Engine: requisições, formatos e o que é reproduzível localmente

> **Data:** 2026-10-05 · **Modo:** estático (`.so` 3.10.0) + leitura dos nossos artefatos + consolidação de observações de runtime. **Nenhuma mudança funcional**: nada de launcher, TLS/trust/pinning, autenticação, anti-cheat, endpoints, dvars, `libgame.so` ou APK. Sem bypass de proteções.
> **Artefato:** `analysis/wzm310/libgame.so` — 91.196.224 B, SHA‑256 `9796040c94cc5876264ace82e623f084b7554040689305222d3abc8a1fb68680` (reextraído e conferido nesta rodada).
> **Objetivo de longo prazo considerado aqui (palavras do usuário):** preservação/interoperabilidade offline em que `WZM → hostname original → DNS/roteamento local → servidor local → respostas/manifests/config locais`, **sem** continuar dependendo dos servidores oficiais.
> **Rótulos:** `VERIFIED` · `PROBABLE` · `HYPOTHESIS` · `UNKNOWN`.
> **Veredito M4.8 (`PREENGINE_META_JAVA_CADEIA_PARCIALMENTE_REPRODUZIVEL`):** o primeiro salto está **fechado** (`com.activision.game.preenginetasks.MetaFetchTask` → `HttpURLConnection`/`com.android.okhttp` → `GET …/_manifest/cdni.meta`). Depois dele a cadeia se **bifurca** em (a) CDNI nativo de conteúdo (`environment.config`, `cdni_manifest_*`, `.shard`, `qos`) e (b) WebView de pré-login (`build-selector-103.js` → shutdown / cadeia `manifest.json` → `boot-*`). **Só o `cdni.meta` é reproduzível hoje com bytes reais** (corpo real versionado no repo); a cadeia WebView é pública e sem autenticação (reproduzível **em princípio**, mas os bytes não estão arquivados aqui); os manifests/shards do CDNI nativo são **opacos/criptografados** e não são reproduzíveis. Mesmo com DNS e roteamento resolvidos, **entregar HTTPS no hostname original exige decisão sobre confiança** — nada disso foi alterado nesta etapa.

## 7. Arquitetura de preservação — avaliação honesta do modelo `WZM → hostname → DNS/rota → servidor local`

| Camada | Situação hoje | Bloqueio |
|---|---|---|
| **1. Resolução do nome** | consulta real acontece (netd, 4,2 s, NODATA) mas **não chega ao nosso DNS virtual**; o app mantém requisições `NOT_VPN` | identificar o `netId 8952` e a rede default do UID 10692 (§9, N1) |
| **2. Roteamento/bounce** | pronto: se o nome resolvesse para `10.111.222.1`, o TCP cairia nas rotas do túnel | — |
| **3. TLS no hostname original** | **bloqueio estrutural**: o cliente exige certificado válido para `prod.cdni.callofduty.com`; nosso listener usa certificado próprio | **não se resolve sem mexer em confiança** (CA de usuário + `network-security-config` do app — desconhecido para 3.10.0 — ou confiança em nível de dispositivo). Nada foi alterado, por restrição explícita |
| **4. Conteúdo** | `cdni.meta` OK; cadeia WebView pública mas **não arquivada**; manifests/shards opacos | decisão de arquivamento + formatos |
| **5. Cliente não desviar** | `UNKNOWN` — indícios (`NOT_VPN`, ausência de pacotes no TUN) sugerem desvio | N1/N3 |

**Conclusão franca:** o modelo de preservação é o correto para o objetivo de longo prazo, e **a camada de conteúdo é parcialmente viável** (`cdni.meta` já; cadeia WebView se arquivada). Mas, **com a restrição de não alterar TLS/trust**, nenhuma configuração de DNS/rotas fará o cliente aceitar uma resposta HTTPS nossa no hostname original — ele trocará `UnknownHostException` por um erro de handshake. É uma decisão que terá de ser tomada explicitamente mais adiante; nada foi feito agora.

Nota útil: `http://cod-assets.cdn.callofduty.com:80/…` mostra que **nem tudo no cliente exige TLS** — se partes dos assets forem servidas em claro, essa fatia poderia ser preservada sem tocar em confiança. Papel exato: `UNKNOWN`.
