# M4.5 — Cadeia estática do WZM 3.10.0 até o primeiro `connect()`/DNS

> **⚠ Aviso de procedência (2026-10-05):** este documento foi escrito sobre um `libgame.so` de 88.132.224 bytes (SHA‑256 `28ba7995…eb054b`), cujo `buildinf` crava `changelist=17654269` — ou seja, o build **3.3.4**, e **não** o 3.10.0 instalado. A partir de M4.6, por decisão do usuário, a análise passou a ser feita **exclusivamente** em `analysis/wzm310/libgame.so` (91.196.224 B, SHA‑256 `9796040c…8680`, `changelist=19854920`). **Todos os endereços, limites de função e xrefs destas páginas são inválidos para aquele arquivo.** O documento fica preservado apenas como metodologia e narrativa histórica; consulte [M4.6](m4.6-manifest-processos-e-cruzamento.md) para os fatos válidos sobre o binário do build instalado.

> **Escopo:** investigação **estática e somente leitura** de `libgame.so` (WZM 3.10.0). **Nenhuma mudança de código** foi feita nesta etapa: nada de TLS/pinning, VpnService/TUN, DNS, endpoints, dvars, APK ou o binário do jogo.
> **Evidência:** binário extraído de `origin/main:libgame.so` (commit `2962105bb94dd622a264d3698dea2c5ddc2628e8`, 2026-10-05), 88.132.224 bytes, SHA-256 `28ba79956008c3465e4d41426c1f8093330c32a227759c8ce54fd35974eb054b`. Conferido byte a byte contra o Git no momento da análise (Apêndice A).
> **Método:** `readelf`, varredura própria de AArch64 (índice de xrefs `ADRP+ADD` e `ADRP+LDR/STR`, índice de chamadores `BL`, limites de função por `.eh_frame_hdr`) e desmontagem pontual com capstone.
> **Fora de escopo:** auth/Demonware, anti-cheat, payload, chaves, corpos HTTP, qualquer alteração de comportamento do launcher.
> **Rótulos usados:** `VERIFIED` (lido direto do binário, reproduzível), `PROBABLE` (inferência forte sobre código verificado), `HYPOTHESIS` (plausível, não confirmada), `UNKNOWN` (não decidível estaticamente).

## 2. Achados que mudam o modelo mental (ordenados por impacto)

### 2.1 `cdni.meta` **cruza para Java** — o pedido pode não sair de dentro do `.so`

`VERIFIED` — a URL `https://prod.cdni.callofduty.com/wzm/shard_cdn/android/_manifest/cdni.meta` (`0x4cbcb8`) tem **uma única referência** em todo o binário, no thunk:

```
0x2506388  ldr  x8, [x0]              ; x0 = JNIEnv* → tabela de funções JNI
0x250638c  adrp x1, #0x4cb000
0x2506390  add  x1, x1, #0xcb8        ; "https://prod.cdni.callofduty.com/wzm/shard_cdn/android/_manifest/cdni.meta"
0x2506394  ldr  x2, [x8, #0x538]      ; índice JNI 167 = NewStringUTF   (167 * 8 = 0x538)
0x2506398  br   x2                    ; return env->NewStringUTF(env, URL)
```

O endereço desse thunk aparece como dado em `0x250ab68`, **dentro de `JNI_OnLoad`** (`adrp x17,#0x2506000; add x17,x17,#0x388; stp x10,x17,[x8,#0x20]`), i.e. é um método nativo registrado via `RegisterNatives`.

**Consequência (PROBABLE):** algum componente **Java/Kotlin** do jogo obtém a URL do CDNI por JNI e executa o HTTP fora do `libgame.so`. Isso importa para o launcher porque:

* um pedido feito em Java passa pela VPN do mesmo jeito, **mas** o cliente, o resolvedor, o proxy e o cache são os do runtime Android (não o curl embutido);
* qualquer checagem Java prévia (estado de rede, `ConnectivityManager`, política de CGI) acontece **antes** de existir socket — e é invisível no TUN.

`UNKNOWN`: qual método Java (nomes das classes JNI são construídos em runtime/ofuscados — ver 2.6) e qual cliente HTTP Java é usado.

### 2.2 Existe **também** um caminho nativo para o `cdni.meta`

`VERIFIED` — há uma **segunda cópia** da mesma URL em `0x5b4158`, referenciada por código nativo:

```
0x2bb3ff4  adrp x2, #0x5b4000
0x2bb3ff8  add  x2, x2, #0x158        ; "https://prod.cdni.callofduty.com/wzm/shard_cdn/android/_manifest/cdni.meta"
0x2bb3ffc  mov  w1, #0x2712           ; 10002 — chave de parâmetro
0x2bb4000  mov  x0, x19
0x2bb4004  bl   #0x45f8508            ; set(chave, valor) num objeto de parâmetros
```

A função `0x2bb3f40` (1.644 B) começa chamando helpers da área JNI (`0x251ed30`, `0x251ec9c`) e monta um objeto de parâmetros (timeout `0xbb8` = 3000 ms na chave `0x9b`). `PROBABLE`: é o agendamento do download do `cdni.meta` por uma camada de tarefas (não por chamada direta), o que explica por que não há `BL` direto para ela.

### 2.3 O "fence" de pre-login e o literal `"disabled"`

`VERIFIED` — dentro da função de registro CDNI/pre-login (`0x114dfa0`–`0x11509ec`, 10.828 B):

```
0x114e344  ldr x8,[GOT 0x536d688] → ldr x8,[x8] → ldrb w8,[x8,#0x28]
0x114e354  tbnz w8,#0 → 0x114e3c0        ; flag ligada: PULA o fetch de pre-login
0x114e358  x22 = [GOT 0x536d690] → [x8,#0x28]      ; ponteiro para string de ambiente/servidor
0x114e368  cbz  x22 → 0x114e3dc                    ; sem string → 0x5c8ad74 = 0 (não passou)
0x114e374  strncpy(0x53905b8, x22, 0x800)          ; copia a string para o buffer
0x114e388  strncmp("disabled", x22, 9)             ; 0x554bc4, PLT strncmp 0x5226e10
0x114e3b0  strb w10,[0x5c8ad74]                    ; 1 se a string == "disabled"
0x114e3b8  cbnz w0 → 0x114e3f0                     ; se NÃO for "disabled": sai SEM publicar o estado
0x114e3d4  bl 0x10b46d0                            ; publica "fence passou" (0x5a38290…), sem rede
```

Leitura (`PROBABLE`, semântica; bytes são `VERIFIED`):

* flag em `objA+0x28` ligada **ou** string de ambiente == `"disabled"` ⇒ o fence é publicado como **passado** e **nenhuma requisição é feita**;
* string ausente ⇒ estado 0 em `0x5c8ad74` (falha explícita);
* string presente e diferente de `"disabled"` ⇒ o fence **não** é publicado aqui; o jogo precisa seguir para o fluxo de rede (pre-login/CDNI) para passá-lo.

`UNKNOWN`: quem escreve `objA+0x28` e a string de ambiente. Os slots GOT `0x536d688`/`0x536d690` têm **exatamente 1 xref cada** (só as leituras acima), e cada um aponta para um endereço distinto de `.bss` (`0xb1c9b50`, `0xb1c9b28`) sem duplicatas na tabela de relocações — ou seja, os escritores chegam ao objeto por outro caminho (acessador/fábrica), não por símbolo global.

### 2.4 Portões de rede que vêm de **Java** (candidato forte a "travou sem socket")

`VERIFIED`:

* flags globais de estado de rede em `.data`: `0x539e198`, `0x539e199`, `0x539e19a` (lidas por `0x143b548/0x143b554/0x143b560`).
* `0x143b594` (setter/propagador): recebe 5 booleanos (`w0..w4`), compara com o estado corrente, grava e dispara eventos.
* `0x143c7a8` e `0x143c7dc` são wrappers que convertem inteiros em booleanos e chamam `0x143b594` — **sem chamadores diretos e sem xref como dado**, padrão idêntico ao dos métodos registrados por JNI.

* **ausência verificada:** não há qualquer string `ConnectivityManager`, `NetworkCapabilities`, `TRANSPORT_`, `getActiveNetwork`, `android.net`, `java.net`, `HttpURLConnection` ou `OkHttp` no `.so`.

`PROBABLE`: o estado de rede é empurrado de Java para o nativo por JNI; o nativo **não** consulta as APIs de conectividade do Android diretamente.

`HYPOTHESIS` (relevante para M4.4): com a VPN do launcher ativa, se o estado publicado por Java não autorizar o download (ex.: "não é Wi-Fi"), a máquina de estados do CDNI pode estacionar sem abrir socket — o que produziria exatamente o quadro observado (contadores de TUN/TCP/DNS em zero).

## 3. Respostas aos seis itens pedidos

### (1) Cadeia de chamadas responsável pelo primeiro pedido de update/bootstrap

`PROBABLE` (topologia `VERIFIED`, nomes `UNKNOWN`):
`init_array` / `JNI_OnLoad` → (registro de comandos e dvars do CDNI em `0x114dfa0`) → máquina de estados do CDNI `0x151155c` → `bdHttpRequest` (`0x33f2154`) → `0x33f2dd4` → `bdHTTPWorker(CURL)`/`(Android)` → libcurl → `getaddrinfo` → `socket/connect`.
Ressalva `VERIFIED`: **nenhum** dos elos centrais (`0x151155c`, `0x1511338`, `0x33f2dd4`, `0x1560384`, `0x2bb3f40`, `0x114dfa0`) tem chamador `BL` direto — a ligação é feita por despacho virtual/tabela em runtime. A cadeia acima é a leitura mais provável, **não** uma cadeia comprovada por grafo de chamadas.

### (2) Processo principal ou processo/helper separado

* `VERIFIED`: toda a pilha de rede (curl, OpenSSL, resolvedor, `bdHTTP`) está **dentro de `libgame.so`**, sem `DT_NEEDED` para bibliotecas de rede.
* `VERIFIED`: o `.so` referencia classes do **Android Game Development Kit** (`com/google/androidgamesdk/GameActivity`, `gametextinput/InputConnection`, `paddleboat/GameControllerManager`) — o elo Java↔nativo é o `GameActivity`.
* `UNKNOWN`: se existe processo auxiliar (ex.: serviço de download). O `AndroidManifest.xml` não foi analisado nesta etapa (M4.5 é estático e restrito ao binário) e o `.so` não contém nomes de processo/serviço. **Não afirmar** processo único nem múltiplo.
* `HYPOTHESIS`: a existência de `bdHTTPWorker(Android)` (implementação Java do mesmo worker) sugere que pelo menos parte do transporte pode ocorrer por código Java no processo que carrega a lib.

2. portão de Wi-Fi/celular do CDNI (2.4/2.5) — espera autorização antes de criar socket;
3. estado persistido do CDNI (`CDNI_RestoreState`, `cdni.pid`, `isCDNIFinished`) — pode pular/passar etapas;
4. dvars/comandos de servidor (`CDNI_UseDevServer`, `cdni_update_show_using_dev`, `CDNI_100_PARSE_MANIFEST`) — trocam a base URL;
5. no caminho Java (2.1), checagens do runtime Android ficam **antes** de qualquer socket.

### (4) `prod.cdni.callofduty.com` é mesmo o primeiro host?

* `VERIFIED`: é o host do `cdni.meta` (duas rotas: JNI→Java e nativa) e do pre-login WebView.
* `PROBABLE`: é o primeiro host **do fluxo de update/bootstrap** (é a base usada pelo estado que constrói o request).
* `UNKNOWN`: o primeiro host **de verdade** na execução — não decidível estaticamente. Concorrentes: `profile.callofduty.com` (upgrade, exposto a script — `PROBABLE` não automático), hosts Demonware (pós-login) e `api.ipstack.com` (geo).
* `HYPOTHESIS`: se o fence de pre-login não for publicado, o WebView de pre-login (`prelogin/web/index.html`) pode ser o primeiro contato — e ele é aberto por código **Java**, fora do curl.

### (5) Condições de build/ambiente/config que param o WZM em "Conectando a servidor de atualizações" sem socket

Ordenado por plausibilidade (`HYPOTHESIS`, com base `VERIFIED`):

1. **Portão de rede vindo de Java** (2.4): estado "sem Wi-Fi/rede não autorizada" ⇒ máquina do CDNI parada em checagem. Explicaria zero TCP/DNS.
2. **Fence de pre-login não resolvido** (2.3): sem publicar "passou", o jogo não avança para o pedido; a tela de espera permanece.
3. **O pedido sai por Java** (2.1) e morre numa checagem do runtime Android antes do socket — invisível ao TUN e ao `libgame.so`.
4. **Estado do CDNI persistido** (`CDNI_RestoreState`, `cdni.pid`) levando a um estado que aguarda intervenção (popups `CDNICellularDownloadTip`, `CDNIGoToAppStorePopup`, `CDNIRecoverableErrorPopup`).
5. **Build/ambiente**: `CDNI_UseDevServer` / `cdni_update_show_using_dev` trocando a base para `dev.cdni.callofduty.com` — `PROBABLE` que exista, `UNKNOWN` se aplicável ao caso.

Nenhuma dessas hipóteses foi testada dinamicamente; M4.5 não altera código nem executa o jogo.

## 4. Limites desta leitura (para não virar "fato" no próximo passo)

* Binário **stripped** (sem `.symtab`, 465 símbolos dinâmicos) e com nomes de comandos/dvars/lua **hasheados em 64 bits**: rótulos como "CDNI", "pre-login" e "fence" vêm de **strings** sobreviventes, não de símbolos.
* As tabelas de `RegisterNatives` e de classes JNI são **montadas em runtime** (nomes construídos na pilha, com aritmética ofuscada em `JNI_OnLoad`): não é possível listar os métodos Java estaticamente.
* Grande parte das ligações é por **despacho virtual**; o grafo de `BL` não cobre essas arestas (por isso vários nós centrais têm zero chamadores diretos).
* Este documento descreve **capacidades e portões existentes no binário**, não o que de fato aconteceu na sessão M4.4. Confirmar qual portão disparou exige instrumentação (que **não** faz parte de M4.5 e, se vier, seguirá as restrições de M3.2/M3.5: sem bypass de TLS/pinning, sem root/Frida).
