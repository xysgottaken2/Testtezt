# M5.4 — Teste comportamental: o WZM 3.10 aceita CA de usuário?

> **Data:** 2026-10-05 · **Modo:** procedimento para execução **no aparelho, pelo usuário**. Nada foi implementado, nenhum certificado foi instalado pelo agente, nenhum código mudou.
> **Limite declarado:** o ambiente do agente **não tem acesso ao dispositivo** (sem `adb`, USB ou sessão). O teste é executado por você; este documento é o roteiro exato, reversível e sem ambiguidade.
> **Objetivo único:** descobrir se o WZM 3.10 confia numa **CA instalada como credencial de usuário** no fluxo do `cdni.meta`.
> **Sem:** alterar o APK, alterar TUN/DNS/roteamento, pinning bypass, hook, alteração da trust store de sistema, modificação permanente.
> **Base:** M5.2 (o redirecionamento funciona até o listener, UID 10692 confirmado) e M5.3 (a regra do AOSP: apps com `targetSdk ≥ 24` confiam só em CAs de sistema, salvo opt-in).

---

## 0. Por que este teste é decisivo

A regra da plataforma (AOSP, `VERIFIED` em M5.3) diz que `targetSdk ≥ 24` ⇒ CAs de usuário **não** entram por padrão. Mas a regra depende de dois fatos do APK. O teste comportamental resolve sem precisar do APK:

| Resultado | Interpretação |
|---|---|
| Handshake **passa** e o `GET …/cdni.meta` aparece | CAs de usuário **são** confiadas pelo WZM → caminho legítimo existe |
| `motivo=CLIENTE_RECUSOU_CERTIFICADO` **igual a antes** | CAs de usuário **não** são confiadas (ou há pinning/`TrustManager` próprio) |
| `motivo=` **muda** para `CERTIFICADO_EXPIRADO`, `HOSTNAME_DIVERGENTE` ou outro | a CA **passou** a ser considerada (o bloqueio agora é outro) — grandes notícias |

## 1. Antes de tudo: o `targetSdk` (custo zero, sem tocar em nada)

Rode **antes** de instalar qualquer coisa — ele dá a resposta esperada e ajuda a interpretar o teste:

```bash
adb shell dumpsys package com.activision.callofduty.warzone | grep -iE "targetSdk|versionCode|flags|debuggable"
adb shell pm dump  com.activision.callofduty.warzone | grep -iE "targetSdk|flags"
```

Anote `targetSdk=`. Se for **≥ 24**, a expectativa (pela regra da plataforma) é `CLIENTE_RECUSOU_CERTIFICADO` de novo.

---

## 2. Obter a CA correta (a que assinou o certificado do launcher instalado)

**Importante:** não adianta gerar uma CA nova — o certificado servido pelo launcher instalado foi assinado pela CA gerada **naquele build**. A CA pública correta está dentro do APK do launcher, como asset (`CdnRouterConfig.CA_ASSET = "cdn_local_ca.pem"`, copiada por `scripts/generate-local-cdni-cert.sh` passo 5/5, já com `basicConstraints=critical,CA:TRUE`).

```bash
# 2.1 onde está o APK do launcher instalado
adb shell pm path com.wzm.launcher
#    → package:/data/app/~~XXXX==/com.wzm.launcher-YYY==/base.apk

# 2.2 trair o APK e extrair só a CA pública
adb pull /data/app/~~XXXX==/com.wzm.launcher-YYY==/base.apk launcher-installed.apk
unzip -p launcher-installed.apk assets/cdn_local_ca.pem > wzm-local-ca.crt

# 2.3 conferir (deve mostrar o subject da nossa CA descartável)
openssl x509 -in wzm-local-ca.crt -noout -subject -issuer -dates
openssl x509 -in wzm-local-ca.crt -noout -text | grep -A2 "Basic Constraints"
# esperado: O=WZM Offline Preservation / CN=WZM Offline Local CDNI CA (throwaway)
#           CA:TRUE · validade 3650 dias (não é problema de expiração)

# 2.4 mandar para o aparelho
adb push wzm-local-ca.crt /sdcard/Download/wzm-local-ca.crt
```

Sem `adb`: gere/instale um build seu do launcher e use o arquivo `android/app/src/main/assets/cdn_local_ca.pem` (o script `scripts/generate-local-cdni-cert.sh` produz exatamente esse par CA+folha).

## 3. Instalar como CA de usuário (reversível)

1. O aparelho precisa ter **bloqueio de tela** (PIN/padrão/senha) — o Android exige.
2. Samsung/One UI: **Ajustes → Segurança e privacidade → Mais configurações de segurança → Instalar do armazenamento do telefone → Certificado de CA** → escolha `wzm-local-ca.crt`.
   (AOSP puro: **Ajustes → Segurança → Mais configurações → Criptografia e credenciais → Instalar certificado → Certificado de CA**.)
3. Aceite o aviso (“a rede pode ser monitorada”). É esperado: é a sua própria CA local.
4. Confira em **Credenciais confiáveis → aba Usuário**.

Não é bypass: não mexe no APK do WZM, não desativa pinning, não toca na loja de sistema.

## 4. Repetir exatamente o mesmo teste

1. **Force-stop no WZM** (para o processo novo carregar as âncoras atualizadas):
   ```bash
   adb shell am force-stop com.activision.callofduty.warzone
   ```
2. Abra o launcher, inicie o roteador (mesma configuração de sempre), confirme `listeners ativos=[10.111.222.1:443 …]`.
3. Abra o WZM e deixe chegar na tela de atualização (mesmo cenário do teste anterior).
4. Capture o log do launcher (tela **VER LOGS** ou `https://prod.cdni.callofduty.com/__wzm_offline/requests`).

O que procurar (linhas com tag `TLS` e `CDNI`):

```text
# ANTES (referência, já observado)
FALHA no handshake TLS em 10.111.222.1:443 (…): motivo=CLIENTE_RECUSOU_CERTIFICADO
  (javax.net.ssl.SSLHandshakeException: … SSLV3_ALERT_CERTIFICATE_UNKNOWN)

# DEPOIS — cenário A (CA de usuário aceita)
handshake OK em 10.111.222.1:443 (…, SNI=prod.cdni.callofduty.com, TLSv1.3) — o cliente aceitou o certificado local
GET /wzm/shard_cdn/android/_manifest/cdni.meta -> 200 (VERIFICADO, 320 B)

# DEPOIS — cenário B (continua recusado)
FALHA no handshake TLS em 10.111.222.1:443 (…): motivo=CLIENTE_RECUSOU_CERTIFICADO
```

Envie também os contadores do health (`/__wzm_offline/health`): `tlsOk`, `tlsFailed`, `httpRequests`, `unknownRequests`.

## 5. Remover a CA (rollback obrigatório)

**Ajustes → Segurança e privacidade → Mais configurações de segurança → Credenciais confiáveis → aba Usuário → toque na nossa CA → Remover.**

```bash
# conferir que não sobrou nada
adb shell ls /data/misc/user/0/cacerts-added/ 2>/dev/null
```

Nada mais precisa ser desfeito: o APK do jogo não foi tocado, o launcher não mudou, a loja de sistema não mudou.

## 6. Tabela de decisão (o veredito sai daqui)

| `motivo=` depois da CA | Veredito “CA de usuário resolve” | Blocker restante |
|---|---|---|
| `handshake OK` + `GET …/cdni.meta → 200` | **VERIFIED** | nenhum no caminho TLS |
| `CLIENTE_RECUSOU_CERTIFICADO` (inalterado) | **REFUTED** | confiança/pinning (não TUN/DNS/rota) |
| `CERTIFICADO_EXPIRADO` / `HOSTNAME_DIVERGENTE` | **VERIFIED** (a CA passou a valer) | detalhe do certificado local, contornável |
| `SEM_CIFRA_COMUM` / `CLIENTE_ENCERROU` | **UNKNOWN** (inconclusivo) | repetir; investigar protocolo |

Se der **REFUTED**, confirmo expressamente no fechamento: **o blocker restante é trust/pinning — não TUN, não DNS, não roteamento** (já provado em M5.2: DNS ✔, bounce ✔, listener ✔, owner UID 10692 ✔, o alerta TLS é gerado **no nosso listener**).
