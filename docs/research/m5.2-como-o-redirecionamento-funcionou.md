# M5.2 — Como o redirecionamento funcionou: anatomia do caminho que levou o WZM ao servidor local

> **Data:** 2026-10-05 · **Modo:** investigação do código existente. **Nada foi implementado, nada foi alterado.** Nenhuma linha de launcher, DNS, TUN, TLS ou APK mudou nesta etapa.
> **Gatilho:** runtime relatado pelo usuário — as conexões no listener **pertencem ao UID do WZM (10692)** e o handshake termina em `CLIENTE_RECUSOU_CERTIFICADO` / `SSLV3_ALERT_CERTIFICATE_UNKNOWN`, sem chegar ao `GET /wzm/shard_cdn/android/_manifest/cdni.meta`.
> **Objetivo:** entender exatamente o que já funcionava (e por quê), para decidir se o mesmo mecanismo serve ao `cdni.meta` antes de escrever qualquer código novo.
> **Rótulos:** `VERIFIED` (lido no código/artefato) · `PROBABLE` · `HYPOTHESIS` · `UNKNOWN` · `[RU]` = relatado pelo usuário em runtime.
> **Veredito M5.2 (`REDIRECIONAMENTO_VPN_DNS_BOUNCE_TLS_ANTES_DO_HTTP`):** o mecanismo é **`VpnService`/TUN + DNS autoritativo dentro do túnel + re-injeção do pacote (“bounce”) + listener HTTPS local**. Não há iptables, não há DNAT/redirecionamento de porta, não há proxy (nem `CONNECT`), não há hosts-file e não há modificação do APK. O mecanismo é **agnóstico ao endpoint**: ele serve ao `cdni.meta` exatamente como serviu a qualquer outro path. O que falta **não é redirecionamento**: é o TLS, que acontece **depois** do TCP e **antes** do HTTP — por isso a requisição nunca é lida.

| # | Pergunta | Resposta |

| 2 | VpnService/TUN, DNS, socket local, redirect de porta ou outro? | **VpnService/TUN é a base**: `addAddress(10.111.222.1/32)`, `addDnsServer(10.111.222.2)`, `addRoute(10.111.222.0/24)`, `addAllowedApplication("com.activision.callofduty.warzone")` (linhas 168–183). O “redirecionamento” é **DNS responder com o IP do próprio túnel** + **bounce** (re-injeção do pacote no TUN, `handleBounce()` 654). **Não há** iptables, **não há** tradução de porta (a porta de destino é preservada) e **não há** proxy. |
| 3 | Fluxo exato | §3 abaixo, passo a passo com arquivo:função. |
| 4 | Reutilizável para o `cdni.meta`? | **Sim, integralmente** — e já está montado: a rota existe em `BootstrapEndpoints` (linha 135) com o corpo real de `CdniMetaBody`, e `CdnRouteTable.respond()` (linha 30) a atende. O único obstáculo é o TLS (§6). |
| 5 | Onde o TLS entra e por que falhou? | Em `LocalHttpsServer.handle()` → `sslSocket.startHandshake()`. Ele ocorre **depois** do bounce e **antes** de `TcpRelay.serve()`, portanto antes de qualquer byte HTTP ser lido. Falhou porque a CA local não está no conjunto de confiança do cliente (§6). |

## 3. O fluxo exato

```
[1] WZM (UID 10692) pede resolução de prod.cdni.callofduty.com
      │  java.net.InetAddress → netd → DNS da rede VPN (addDnsServer 10.111.222.2)
      ▼
[2] Pacote UDP/53 → 10.111.222.2 entra no TUN  (rota 10.111.222.0/24 instalada por addRoute)
      │  CdnVpnService.loop() → handlePacket() → IpPacketParser.parse → TunPolicy.decide()
      ▼
[3] TunAction.RESPOSTA_DNS → handleDns() → DnsResponder.answer()
      │  A = 10.111.222.1   (AAAA/SVCB = NOERROR vazio)
      ▼
[4] Resposta escrita de volta ao TUN ("tunel->app"); contador dnsIntercepted++
      ▼
[5] WZM abre TCP para 10.111.222.1:443  (SYN)
      │  entra no TUN pela mesma rota
      ▼
[6] TunPolicy.decide(): isTcp && isCdnTargetV4 → TunAction.BOUNCE → handleBounce()
      │  registra o owner UID (getConnectionOwnerUid) e re-injeta o pacote SEM alterar porta/IP
      ▼
[7] O kernel entrega ao listener local 10.111.222.1:443  (LocalHttpsServer, papel TUNEL_PRIMARIO)
      │  acceptLoop(): owner UID do peer == UID-alvo → "owner-UID-alvo-confirmado=true"
      ▼
[8] handle(): sslSocket.startHandshake()          ← ★ O TLS COMEÇA AQUI ★
      │  cliente não confia na CA local → alerta 46 (certificate_unknown)
      ▼
[9] SSLHandshakeException → TlsTrust.analyze() → motivo=CLIENTE_RECUSOU_CERTIFICADO
      │  TcpRelay.serve() NUNCA é chamado → nenhum byte HTTP é lido → o GET não aparece
      ▼
[10] (se o handshake passasse) TcpRelay.serve() → CdnRouteTable.respond() → 200 com o corpo real
```

**Leitura do seu log com este mapa:** você observou exatamente os passos **[1] → [8]** com sucesso, e a parada no **[9]**. Ou seja: DNS ✔, rota ✔, bounce ✔, listener ✔, dono da conexão ✔ — e **TLS ✘**. O fato de o alerta ter acontecido **no nosso listener** é a prova de que o redirecionamento está completo e funcionando.

## 4. O que o mecanismo **não** é (evidência negativa)

| Mecanismo | Presente? | Evidência |
|---|---|---|
| iptables / NAT no kernel | **Não** | nenhuma chamada; o processo é todo em userspace sobre o fd do TUN |
| Redirecionamento de porta (DNAT/REDIRECT) | **Não** | `handleBounce()` re-injeta o pacote **sem alterar** IP/porta de destino; por isso o listener precisa estar na **443** (o fallback 18443 não atende um pacote endereçado à 443) |
| Proxy HTTP (`CONNECT`) | **Não** | não há tratamento de `CONNECT`; conexão em claro é tratada como HTTP direto (`TlsTrust.CLIENT_CLEARTEXT`) |
| Arquivo `hosts` / configuração do sistema | **Não** | a resolução vem de `addDnsServer` + `DnsResponder` no TUN |
| Alteração do APK do jogo | **Não** | nada no launcher toca no pacote do WZM |
| Componente exportado / Intent para o jogo | **Não** | o launcher não envia nada ao WZM; o acoplamento é só rede |

## 5. Reutilização para o `cdni.meta` (pergunta 4)

**Sim.** O mecanismo é independente de path e de host (desde que o host caia em `DnsResponder.isIntercepted()`), e a peça final já está pronta:

| Etapa | Situação para o `cdni.meta` |
|---|---|
| Host coberto pelo DNS | `prod.cdni.callofduty.com` é o `EXACT_HOST` → `VERIFIED` |
| Rota no servidor | `BootstrapEndpoints` linha 135 (path exato) → `VERIFIED` |
| Corpo da resposta | `CdniMetaBody` — **corpo real** (`min_buildnum=19854920`) → `VERIFIED` |
| Content-type/headers | `HttpResponses.build` + `X-WZM-Offline` → `VERIFIED` |
| Registro de desconhecidos | `CdnRouteTable.unknown()` → 404 com method/path/host → `VERIFIED` |
| **TLS** | **único bloqueio** → ver §6 |

Conclusão: **não é necessário nenhum mecanismo novo de redirecionamento para o `cdni.meta`.** Se o handshake passasse, a próxima linha do log seria `GET /wzm/shard_cdn/android/_manifest/cdni.meta → 200 (VERIFICADO, ~320 B)`.

## 6. Onde o TLS entra e por que falhou (pergunta 5)

**Onde:** `LocalHttpsServer.handle()` chama `sslSocket.startHandshake()` **antes** de `relay.serve(...)`. O HTTP só é lido depois do handshake — e é por isso que **nenhum path aparece no log**: a requisição existe, mas nunca é entregue ao parser.

**O que o cliente recebe:** o certificado do PKCS12 local (`scripts/generate-local-cdni-cert.sh`): CA descartável nossa + leaf com `CN=prod.cdni.callofduty.com` e SANs corretos. **Nome e SANs estão certos** — o problema é a **cadeia**: a CA emissora não está no conjunto de âncoras de confiança que o cliente usa.

**Por que falhou (`VERIFIED` o código, `PROBABLE` a causa):**

1. O cliente é `HttpsURLConnection` → `com.android.okhttp`, que valida com o `TrustManager` padrão (âncoras do sistema).
2. Nossa CA é privada e não está lá → o cliente envia o alerta TLS **46 `certificate_unknown`** e fecha.
3. O `SSLServerSocket` levanta `SSLHandshakeException`; `TlsTrust.analyze()` classifica como `CLIENTE_RECUSOU_CERTIFICADO`.
4. `SSLV3_ALERT_CERTIFICATE_UNKNOWN` é o **alerta do cliente**, não um erro do nosso lado: ele confirma que **o cliente chegou, recebeu o certificado e o rejeitou** — não é timeout, não é reset, não é falta de rota.

**O que ainda é `UNKNOWN` e decide o remédio:**

| Pergunta | Por que importa | Como responder |
|---|---|---|
| O WZM 3.10 aceita **CA de usuário**? | Se aceitar, instalar nossa CA como credencial de usuário resolve **sem root e sem tocar no APK** | `res/xml/network_security_config.xml` + `android:networkSecurityConfig` no `AndroidManifest.xml` do WZM |
| Existe **pinning** (`<pin-set>` / `CertificatePinner`)? | Se existir, nem uma CA confiável passa | mesmo arquivo + `classes*.dex` do WZM |
| Qual porta realmente vinculou (443 ou 18443)? | o bounce preserva a porta; sem 443 o pacote não acha listener | linha `listeners ativos=[…]` no log do launcher |

## 7. Como testar sem alterar o APK e sem bypass de TLS/pinning (pergunta 6)

Todos os passos abaixo são **leitura/observação** ou usam um cliente que *escolhe* confiar na nossa CA. Nenhum altera o jogo, o APK, a trust store do aparelho para o WZM, nem usa hook/Frida/Xposed.

| Teste | Como | O que prova | O que **não** prova |
|---|---|---|---|
| **T1 · DNS** | rodar o roteador, abrir o WZM, ler `dnsQueries`/`dnsIntercepted` e as linhas `DNS …` no log | a consulta chegou ao nosso respondedor e recebeu `A=10.111.222.1` | que o WZM usou a resposta (provado pelo passo seguinte) |
| **T2 · TCP + dono** | linhas `TCP SYN … -> 10.111.222.1:443 (dono=…) devolvido ao TUN (bounce #N)` e `fluxo do UID do app alvo confirmado` | o WZM conectou ao nosso endereço e o UID confere — **já verificado por você** | qual processo/PID (UID não identifica processo) |
| **T3 · TLS tentado** | linha `FALHA no handshake TLS em 10.111.222.1:443 … motivo=CLIENTE_RECUSOU_CERTIFICADO (… SSLV3_ALERT_CERTIFICATE_UNKNOWN)` | o certificado foi entregue e rejeitado — **já verificado por você** | nada sobre o path (HTTP ainda não existe) |
| **T4 · protocolo + resposta** | com o roteador ligado, peça **de outro app que confie na nossa CA** (ex.: navegador com a CA instalada como credencial de **usuário** — navegadores aceitam CAs de usuário) `https://prod.cdni.callofduty.com/wzm/shard_cdn/android/_manifest/cdni.meta` | o caminho DNS→bounce→listener→rota devolve **200 com o corpo real** | que o WZM aceitará (o jogo só confia em CAs de usuário se o `network-security-config` permitir) |
| **T5 · diagnóstico** | `https://prod.cdni.callofduty.com/__wzm_offline/health` e `/__wzm_offline/requests` (mesmas condições de T4) | contadores (`dnsIntercepted`, `tlsOk`, `tlsFailed`, `unknownRequests`) e o log de requisições | — |
| **T6 · claro** | se algum host for **HTTP** (ex.: `cod-assets.cdn.callofduty.com:80`), o servidor já trata `CLIENTE_FALOU_HTTP_EM_CLARO` e serve sem TLS | o caminho funciona sem nenhuma decisão de confiança | não serve ao `cdni.meta`, que é `https` |
| **T7 · o que o jogo aceita** | extrair `AndroidManifest.xml` + `res/xml/network_security_config.xml` + `classes*.dex` do WZM | se CA de usuário resolve e se há pinning | nada muda no runtime |

**Limite honesto:** os testes T1–T3 você **já fez** e eles provam o redirecionamento. T4–T6 provam **o resto da cadeia** sem tocar no jogo. Mas **fazer o próprio WZM aceitar** exige uma decisão sobre confiança — é o blocker legítimo, e ele **não é** um problema de redirecionamento.

## 9. Classificação consolidada

**VERIFIED** — VpnService/TUN com `10.111.222.1/32`, DNS `10.111.222.2`, rota `10.111.222.0/24`, allow-list do WZM; `DnsResponder` autoritativo (A=`10.111.222.1`, AAAA/SVCB vazio); política `TunPolicy.decide` (DNS→responde, TCP→alvo=bounce, resto descarta); **bounce sem alterar IP/porta**; listeners `10.111.222.1:443` (primário), `127.0.0.1:443` (diagnóstico), `10.111.222.1:18443` (fallback); owner UID por `getConnectionOwnerUid`; handshake **antes** do parse HTTP; rota e corpo real do `cdni.meta` prontos; certificado local com SANs corretos; ausência de iptables/DNAT/proxy/hosts/alteração de APK.

`[RU]` (relatado por você em runtime) — conexões no listener com owner UID **10692**; falha `CLIENTE_RECUSOU_CERTIFICADO` / `SSLV3_ALERT_CERTIFICATE_UNKNOWN`; ausência do `GET …/cdni.meta`.

**PROBABLE** — a rejeição vem exclusivamente da cadeia de confiança (CA local fora das âncoras do cliente), e não de SAN/hostname (os SANs cobrem o host) nem de protocolo/cifra.

**HYPOTHESIS** — que CA de usuário baste (depende do `network-security-config` do jogo); que não haja pinning.

**UNKNOWN** — qual porta vinculou neste aparelho; se o 3.10 aceita CA de usuário; se há pinning; o SNI nas falhas; comportamento IPv6 do cliente.
