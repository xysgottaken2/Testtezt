> **Pergunta central:** *como um launcher externo inicia um backend local e faz o **APK oficial, sem modificação**, usar esse backend?*
> **Rótulos obrigatórios:** `VERIFIED` · `PROBABLE` · `HYPOTHESIS` · `UNKNOWN`.
> **Compromisso:** não reescrever o launcher, não remover nem expandir o VpnService, não implementar bypass de TLS/pinning, não alterar trust store, não modificar o APK oficial, não apagar testes existentes. O código atual de DNS/TUN fica preservado como experimento e evidência.

## 1. Resposta curta: por onde começar

**Sim — começamos com `AndroidManifest.xml` + `classes*.dex`.** Esse par já responde a maior parte das perguntas (componentes, permissões, processos, bibliotecas de servidor, strings de bind/porta, IPC). Todo o resto é segunda onda e só será pedido se a primeira deixar uma pergunta aberta.

| Onda | Artefatos | Obrigatório? | Decide o quê |
|---|---|---|---|
| **1** | `AndroidManifest.xml` (cru **e** decodificado, se conseguir) | **Sim** | pacote, permissões, Activities/Services/Receivers/Providers, `android:process`, exported, intent-filters, schemes, foreground service |
| **1** | `classes*.dex` (**todos**) | **Sim** | onde o servidor é implementado, biblioteca, bind/porta, IPC, endpoints |
| **1** | `file-listing.txt` (`unzip -l`) | **Sim** (custa KB) | revela `assets/`, `res/raw`, `lib/*.so`, nomes de configs, bibliotecas embutidas |
| 2 | `resources.arsc` | Opcional | resolve `@string`/`@integer` (portas e hosts frequentemente vivem em recursos) |
| 2 | `assets/` + `res/xml/` + `res/raw/` (só arquivos de texto/pequenos) | Opcional | configs de servidor, certificados/keystores, HTML/JS, seeds de banco |
| 2 | `lib/<abi>/*.so` | **Só se** o DEX mostrar `System.loadLibrary` relevante | se o servidor (ou o DNS/proxy) for nativo |
| 2 | `badging.txt` (`aapt dump badging`) | Opcional | versionCode/Name, sdk, permissões já resolvidas |
| Bônus | `logcat` + `ss -ltnp` durante o “Start Server” | Opcional | **prova** de bind/porta/UID (vem depois, sem substituir a análise estática) |

Estrutura proposta (committada no branch da sessão para eu conseguir ler):

```
analysis/dbdm-offline/
```

* **Alternativa que preserva tudo:** se preferir não versionar nada, anexe os arquivos na conversa — eu analiso no workspace e não commito nada. O `.dex` **não precisa** ser commitado para eu analisar; o commit só ajuda a manter o histórico.
* Nomes de pacote/versão e o SHA-256 do APK no `README.md` são o que permite aferir se estamos falando do mesmo binário.

## 3. Como extrair cada artefato

### 3.1 Sem instalar nada (`unzip` / `7z` / Python) — sempre funciona

```bash
# 1) listing completo (tiny, altamente informativo)
unzip -l dbdm-offline.apk > file-listing.txt

# 2) manifest + todos os dex + resources
unzip -o dbdm-offline.apk "AndroidManifest.xml" "classes*.dex" "resources.arsc" -d out/

# 3) assets/res (segunda onda)
unzip -o dbdm-offline.apk "assets/*" "res/xml/*" "res/raw/*" -d out/
```

No Windows (sem `unzip`): `7z x dbdm-offline.apk -oout AndroidManifest.xml classes*.dex` — ou, com Python:

```bash
python3 -c "import zipfile,sys; z=zipfile.ZipFile('dbdm-offline.apk'); open('file-listing.txt','w').write('\n'.join('%9d  %s'%(i.file_size,i.filename) for i in z.infolist())); [z.extract(n,'out') for n in z.namelist() if n.endswith('.dex') or n=='AndroidManifest.xml']"
```

### 3.2 Decodificando o `AndroidManifest.xml` (binário AXML)

O `AndroidManifest.xml` dentro do APK é **binário**. Três caminhos, do melhor ao pior:

```bash
aapt2 dump xmltree dbdm-offline.apk AndroidManifest.xml > AndroidManifest.txt   # melhor
apktool d -s dbdm-offline.apk -o dbdm-out                                       # -s não decodifica dex
jadx --no-res -d dbdm-jadx dbdm-offline.apk                                     # só código; manifest em resources/
```

**Fallback sem nenhuma ferramenta (testado aqui):** o *pool de strings* do AXML fica legível no arquivo cru. Isto devolve pacote, nomes de componentes, permissões e schemes (não devolve a estrutura de atributos):

```bash
python3 -c "import re;d=open('AndroidManifest.xml','rb').read();print('\n'.join(s.decode('utf-16-le','replace') for s in re.findall(rb'(?:[\x20-\x7e]\x00){4,}',d)))"
```

Exemplo real validado nesta sessão: `versionCode | versionName | label | name | android | … | package | manifest | org.t0t0.androguard.test | application | activity | .TestActivity | intent-filter | action`.

### 3.3 Dex: **não** é necessário descompilar na primeira etapa

O `warzone-offline/tools/apk-analysis/dex-scan.py` deste repo faz parse do DEX em Python puro e devolve **classe → método → strings → chamadas**, sem jadx e sem extrair para o disco:

```bash
python3 ../../warzone-offline/tools/apk-analysis/dex-scan.py --apk dbdm-offline.apk --stats --list-classes --class-filter "server|Server|http|Http|proxy|Proxy|vpn|Vpn|dns|Dns|socket|Socket"
python3 ../../warzone-offline/tools/apk-analysis/dex-scan.py --apk dbdm-offline.apk \
    --search "127.0.0.1" "localhost" "0.0.0.0" "::1" "ServerSocket" "NanoHTTPD" "ktor" "netty" "OkHttp" \
             "VpnService" "startForeground" "bindProcessToNetwork" "System.loadLibrary" \
    --json /tmp/dbdm/hits.json
```

`jadx` fica como **opcional e recomendado** para a leitura de fluxo (quem chama quem, em que ordem) — mas o plano não depende dele.

## 4. O que cada artefato responde (mapa pergunta → arquivo)

| Pergunta do usuário | Artefato que responde |
|---|---|
| Onde o servidor é implementado; Java/Kotlin ou nativo | `classes*.dex` (+ `lib/*.so` se houver `System.loadLibrary`) |
| Qual biblioteca (NanoHTTPD/Ktor/Netty/okhttp/…) | `classes*.dex` (nomes de classes) + `file-listing.txt` |
| Bind, porta, HTTP/HTTPS, TLS, certificados | `classes*.dex` + `res/raw`/`assets` (keystores `.p12`/`.bks`/`.pem`) |
| Roda no processo do launcher? Como Service? Processo separado? | `AndroidManifest.xml` (`<service>`, `android:process`, `foregroundServiceType`) |
| Como é iniciado/encerrado/monitorado | `classes*.dex` (fluxo de chamadas) + `AndroidManifest.xml` (receivers de boot/broadcast) |
| Onde ficam dados/logs; como sabe que está pronto | `classes*.dex` (paths) + `file-listing.txt` (diretórios de assets/db) |
| **Como o DBDM oficial encontra o servidor** (A–I) | `AndroidManifest.xml` (schemes/deep links/exported/process) **+** `classes*.dex` (strings de host/porta, `Intent`, `bindProcessToNetwork`, `SharedPreferences`, `/data/data/…`, `iptables`, `VpnService`) |
| VPN é usada ou só referenciada? | `AndroidManifest.xml` (**`android.permission.BIND_VPN_SERVICE` e um `<service>` com `android.net.VpnService`** são a evidência forte) + `classes*.dex` (`Builder.establish`, `addRoute`, `addDnsServer`) |
| Comparação com WZM 3.10 | os nossos artefatos atuais + `classes*.dex` **do WZM** (ainda não temos) |

**Regra de evidência para VPN (item 6 do pedido):** só classificarei VPN como parte da arquitetura se houver **serviço VPN declarado + iniciado**, criação de TUN/rotas ou interceptação de tráfego. A presença da string `VpnService` sozinha será registrada como `HYPOTHESIS`, nunca como fato.

## 5. Protocolo de análise (o que eu faço quando os arquivos chegarem)

1. **Procedência** — conferir `README.md` (pacote, versão, SHA-256), listar tamanhos e quantidade de dex.
2. **Manifesto** — componentes, permissões, `android:process`, exported, intent-filters, schemes, foreground service, `networkSecurityConfig`, `usesCleartextTraffic`.
3. **Varrredura de strings** — `127.0.0.1`/`localhost`/`0.0.0.0`/`::1`, portas, `ServerSocket`, `bind`, `listen`, bibliotecas de servidor, `proxy`, `dns`, `iptables`, `VpnService`.
4. **Localizar o servidor** — a classe que abre o socket, o bind, a porta, HTTP vs HTTPS, keystore, ciclo de vida (`start`/`stop`), e quem a chama (Activity “Start Server”? Service? Receiver?).
5. **Cadeia de descoberta (A–I)** — testar cada hipótese do item 5 contra evidência concreta, e marcar cada uma como `VERIFIED` / `PROBABLE` / `HYPOTHESIS` / `UNKNOWN`.
6. **Comparação DBDM × WZM 3.10** — o que é transportável para o nosso caso, o que depende de particularidades do DBDM (ex.: jogo já falar com `localhost`), e o que exigiria root/pinning.
7. **Recomendação arquitetural** — só depois disso, e sem código.

Toda descoberta entra em documento com rótulo explícito; nenhuma hipótese vira fato.

## 6. Complemento dinâmico (opcional, mas decide rápido)

Não substitui a estática; só acelera a confirmação do bind/porta. Rode com o launcher aberto, **depois** de tocar em “Start Server”:

```bash
adb logcat -c
adb logcat | grep -iE "nanohttpd|server|listen|bind|accept|port|127\.0\.0\.1|localhost|vpn"
adb shell ss -ltnp            # quem está escutando, em qual endereço:porta
adb shell dumpsys activity services <pacote.do.launcher>   # serviços vivos e processo
adb shell cat /proc/net/tcp   # alternativa quando `ss` não existe
```

Isso responde “qual endereço/porta e em qual processo” direto do kernel, sem adivinhar.
