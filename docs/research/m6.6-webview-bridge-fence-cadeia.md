# M6.6 — Cadeia `página → WebView → ponte → Java → dispatcher → nativo`, e a condição que tira o WZM do prelogin

<!-- FENCE_NAO_E_GATE: passPreloginFence/closeWebView = teardown+telemetria (0x11d1730); não é semáforo do boot -->

Análise estática (nada foi modificado no APK, TLS/pinning, TUN, DNS ou servidor; nada implementado).
Binário: `analysis/wzm310/libgame.so` — WZM 3.10.0.19854920, SHA-256
`9796040c94cc5876264ace82e623f084b7554040689305222d3abc8a1fb68680` (fora do git, somente `analysis/`).
Método: decodificação manual de AArch64 sem `capstone`/`pyelftools`; tudo abaixo é reproduzível com
`scripts/wzm_native_xref.py` (comandos citados junto de cada afirmação).
Rótulos: `VERIFIED` = medido no binário; `PROBABLE` = medido + interpretação; `HYPOTHESIS` = ainda não medido;
`USER_SUPPLIED` = veio do DEX/relato do usuário (a confirmar); `UNKNOWN` = lacuna assumida.

Contexto: continuação direta de `m6.5` (§6/§7 — as três verificações pedidas: C1 DEX, C2 `passPreloginFence`,
C3 caminho até o CDNI). C2 e C3 foram fechadas aqui; **C1 não pode ser fechada neste workspace** (o APK
3.10.0 não está aqui e não há `dexdump`/`baksmali`); foi entregue a ferramenta (§7).

## 1. Resumo — o mapa pedido

| Elo | Endereço / artefato | Estado |
|---|---|---|
| Página carregada | rotas construídas em `0x1f59078` (`0x1f59078..0x1f5a020`, 1002 instr) | `VERIFIED` |
| WebView (Android) | criada no Java (DEX); do lado nativo só aparecem *eventos* `on_mobile_webview_open`/`on_mobile_webview_close` (`0x4a610d`, `0x53690b`) | `VERIFIED` (nativo) / `USER_SUPPLIED` (Java) |
| Objeto JS exposto | `addJavascriptInterface` ocorre só no DEX; nenhum `android/webkit` no `.so` | `UNKNOWN` até C1 |
| Métodos da ponte | `passPreloginFence`, `closeWebView`, `CDNI_UseDevServer`, `CDNI_UseProdServer`, `saveKVP` | `VERIFIED` (nativos), Java `USER_SUPPLIED` |
| Dispatcher | tabela em `0x11cdaec`; handler gigante `0x11dc520` (6468 instr) | `VERIFIED` |
| Funções nativas | `0x11d1730` (fechar), `0x159f524` (resposta de popup), `0x15ae4f8`, `0x159f078`, `0x159f4e0`, `0x15af1d4` (escolha de base) | `VERIFIED` |

**Resposta curta à pergunta-título:** a condição que faz o WZM sair de update/prelogin e seguir para o
CDNI/engine **não** é `passPreloginFence`. O que o binário mede é:

1. o fechamento da WebView é apenas *teardown + estado interno + telemetria* (§3, `VERIFIED`);
2. existe um **watchdog de ~31 s** que fecha a WebView sozinho, sem nenhuma participação da página (§4, `VERIFIED`);
3. a alavanca real sobre o CDNI é o **conjunto de comandos da ponte que responde popups CDNI**
   (`proceed_anyway`, `use_dev_cdn`, `dont_change` → `0x159f524`), porque `use_dev_cdn` é justamente a chave
   que faz `0x15af1d4` instalar outra base no slot `0x58` do objeto `0x6c142d0` — a mesma base usada pelo
   `cdni.meta` (m6.4) (§5, `VERIFIED`/`PROBABLE`);
4. essa base alternativa vem de um **JSON de configuração lido localmente** (`0x157c3a8`: chaves
   `server_url`, `project_dir`, `shard_cache`), chamado pelo próprio CDNI state machine `0x15a1534`
   (§6, `VERIFIED` nas arestas) — ou seja, é satisfaível com HTTP local, sem tocar em TLS/pinning (`PROBABLE`).

## 3. C2 — o que `passPreloginFence → 0x11d1730` realmente faz (`VERIFIED`)

`0x11dc45c` (`closeWebView`) e `0x11dc460` (`passPreloginFence`) convergem para `0x11d1730`
(`0x11d1730..0x11d1838`, 66 instr). Corpo medido (`refs 0x11d1730`):

| trecho | o que faz |
|---|---|
| guarda em `0x5f84a38` / `0x5f84a39` (`LDRSB`) | `RET` imediato se a byte "WebView ativa" for diferente de zero — reentrância, não semáforo |
| `0x1709380`, `0x1708ae8`, `0x1709684`, `0x1709d34` | helpers do "controller" de índice `54` (o slot da WebView); `0x1709d34` contém `pthread_cond_broadcast` |
| `0x1709e34` | `gettimeofday` + `pthread_cond_timedwait` (espera com prazo) |
| `0x17094c8` (104 instr) | `pthread_mutex_lock/unlock` + **`pthread_join`** — aguarda a thread JS terminar |
| `0x2c6b978("dlog_event_webview_closed")` + `0x2c6ba64` | telemetria: chave `webview_url` = caractere em `0x551e2d8+0xcde`, senão `"None"` |
| `0x567c450 = 1`, `0x567c454 = -1` | publica "fechado" / zera o código de estado |
| `B 0x285bc68` | cauda (liberação de contexto) |

**Leitores desse estado — todos dentro do módulo da WebView.** `flags` dá:

| global | acessos | funções |
|---|---|---|
| `0x567c450` ("fechada") | 3 em 3 | `0x11d1730`, `0x11d1838`, `0x11d1f10` |
| `0x567c454` (código de estado) | 17 em 12 | `0x11d15ec 0x11d16e8 0x11d1730 0x11d1838 0x11d1ea8 0x11d1ebc 0x11d2ff8 0x11d3f18 0x11d44b8 0x11db970 0x11dc190 0x11dc520` |
| `0x5f84a38` (ativa) | 6 em 6 | `0x11d15ec 0x11d1730 0x11d1838 0x11d1ed0 0x11d1f20 0x11d2ff8` |
| `0x5f84a39` | 3 em 2 | `0x11d1730`, `0x11dc520` (único escritor) |
| `0x5f85215` | 5 em 4 | `0x11d1730 0x11d1838 0x11dc190 0x11dc520` |

Faixa `0x11d15ec..0x11dc520` = o módulo WebView inteiro (`0x11d1838` = `on_mobile_webview_open` +
`%s://%s%s` + `isConnected`; `0x11d3f18` = estatísticas `StreamPrefetch*`; `0x11db970` = `webviewdata` /
`game` / `kvps-%d`). Nada na região do CDNI lê essas flags. `reach 0x11d1730 --to <regiões CDNI> --max 8`
retorna **0 caminhos**.

> **Veredicto C2 (`VERIFIED`):** `passPreloginFence` **não** libera semáforo/flag que faça o boot continuar.
> É `join` da thread JS + publicação de "WebView fechada" + DLOG. As duas esperas que ele faz
> (`cond_timedwait`, `pthread_join`) são internas ao controlador `54` da própria WebView; os outros
> chamadores de `0x11d1730` (`0x1130aac`, `0x11dc190`, `0x11dc520`, `0x1dceea0`, `0x1f64990`) são todos
> do módulo WebView ou do frontend/UI, nenhum é o laço de boot do engine.
> O que **ainda é** `UNKNOWN`: se uma classe Java (ex.: `WBootstrap`) bloqueia uma thread própria esperando
> o callback nativo — isso só o DEX responde (§7, C1-3).

## 4. Como se sai do update/prelogin (extra pedido) — 3 saídas medidas

| # | condição | evidência |
|---|---|---|
| A | página chama `passPreloginFence`/`closeWebView` | `0x11dc45c`/`0x11dc460` → `0x11d1730` (§3) — `VERIFIED` |
| B | **watchdog**: `0x1130aac` faz `BL time`, `SUB`, `CMP #0x1f`, `B.lt` → se `elapsed ≥ 31 s` chama `0x11d1730` | chamado só por `0x1dceea0` (7177 instr, bloco de script/UI do frontend) — `VERIFIED` |
| C | nativo empurra estado para a UI: `0x11d16e8(código)` grava `0x567c454` e, conforme o valor, chama o dispatcher `0x11dc520` e/ou `0x11d1838` (abrir/atualizar) | `refs 0x11d16e8` — `VERIFIED` |

Eventos do lado da UI (nomes `XString`, 1 xref cada, `str on_mobile_webview`):

- `on_mobile_webview_open` (`0x4a610d`) ← `0x11d1b54` em `0x11d1838`;
- `on_mobile_webview_close` (`0x53690b`) ← `0x11dde54` em `0x11dc520`;
- `mobile_webview_hide_loader` (`0x536923`) ← `0x11ddea8` em `0x11dc520`.

`VERIFIED`: nenhuma das três saídas depende de TLS/pinning, e **B garante que a tela de prelogin não é
infinita** — a WebView se fecha sozinha depois de ~31 s. Isto é consistente com o observado em `m6.5`
(trocar só o HTML da tela de update fez a tela de shutdown sumir sem liberar nada).

## 5. O que a ponte alcança no CDNI (C3) — as 7 arestas e os comandos

`reach`/`callers` mostram que o **único** ponto por onde o módulo WebView entra na região do CDNI é o bloco
de comandos `0x11dc520` (+ dois acessos do bloco de estado). Arestas completas:

```
0x11d25f4 → 0x159f06c     0x11d2884 → 0x159f394
0x11d8844 → 0x2e34d80     0x11dc520 → 0x159f078 0x159f4e0 0x159f524 0x15ae4f8
```

| alvo | o que é (strings/globais medidos) | efeito |
|---|---|---|
| `0x159f078` (83 instr) | `CDNIErrorPopup`, `CDNIMessagePopup`, `CDNIRecoverableErrorPopup`; global `0x6c1ac80` | texto/estado dos popups da tela de download |
| `0x159f4e0` | `GO_TO_APP_STORE`, `https://www.callofduty.com`; `0x6c16a7c`, `0x6c18e18` | ação "ir para a loja" |
| `0x159f524` (50 instr) | `CDNICellularDownloadPopup`, `CELLULAR_NETWORK_DOWNLOAD*`; `0x6c18e18`; → `0x11d2e2c`, `0x11d2ea8`, `0x1ca8d08` | **registra a resposta do popup CDNI** |
| `0x15ae4f8` (20 instr) | compara `CELLULAR_NETWORK_DOWNLOAD == "YES"` no objeto `0x69e0bb0`, `STRB` em `0x69e160a`, `BL 0x2e3d92c` | persiste consentimento + chama o reset de estado |
| `0x2e3d92c` (451 instr) | string `CDNI_UNDEFINED` (`0x52031c`); globals `0xdd84128/0xdd84348/0xdd84358/0xdd849f0`; chamadores: `0x159f5ec`, `0x15a1534`, `0x15ae4f8` | coloca a máquina de estado CDNI em `UNDEFINED` (reset/reatrelar) |

Os handlers que chegam a `0x159f524` dentro de `0x11dc520` (dump `dis 0x11dcfc0 40`):

```
11dcfc0  ADRP/ADD x0 = "proceed_anyway" ; BL 159f524 ; 2bfd04c("tos","CDNIShowDiskSpaceFailedPopup")
11dd024  ADRP/ADD x0 = "use_dev_cdn"    ; B  159f524
11dd048  ADRP/ADD x0 = "dont_change"    ; BL 159f524 ; 2bfd04c("tos","CDNIPromptUseDevServer")
```

Ou seja: **a ponte responde popups do CDNI por string**, e a resposta é persistida no acesso `0x2bfd04c`
(mesmo acessor de `saveKVP`, mas na seção `tos`, não `game`/`kvps` — `VERIFIED`). `proceed_anyway` também é
lida pela própria máquina de estado `0x15a1534` (`str proceed_anyway`: xrefs em `0x11dc520` e `0x15a1534`).

E o elo que faltava (`VERIFIED`):

```
0x15af1d4..0x15af578 (233 instr)   "use_dev_cdn" (0x15af490)  "LimitEnabled"  "cdni_update_show_using_dev" (0x15af538)
    lê flag em 0x6c15d90, objeto base 0x6c142d0, campo +0x1ac0,
    depois LDR x8,[x8,#0x58]; BLR x8      <-- mesmo slot 0x58 identificado no m6.4 como gravador da base
    e emite cdni_update_show_using_dev; cauda: 0x11d2968, 0x11d2a48 (volta ao módulo WebView)
```

`0x15af1d4` é chamado por `0x157c3a8`, `0x157feb0`, `0x15802d0` (§6).

> **Conclusão C3 (`PROBABLE`):** a ponte **não** age sobre o CDNI pela cerca/fechamento, e sim pelas
> *respostas de popup* — e `use_dev_cdn` é exatamente a chave consultada por quem instala a base do CDNI.
> Direção contrária também existe (`0x15a1534 → 0x11d25f4/0x11d2968/0x11d3334`, `0x15af1d4 → 0x11d2968/0x11d2a48`,
> `0x159f1c4 → 0x11d2c00`): o CDNI pilota a WebView, não o contrário.

## 7. C1 — o que o DEX precisa responder (não dá para fechar aqui)

Nenhuma ocorrência de `android/webkit`, `addJavascriptInterface`, `@JavascriptInterface`,
`shouldInterceptRequest` em `libgame.so` (`VERIFIED`): isso é 100% Java/DEX. O launcher do repo serve hoje
um HTML de placeholder em `/static/web/index.html` e os corpos de `cdni.meta` (`BootstrapEndpoints.kt`),
mas **não** carrega uma página com a ponte. Ferramenta entregue para rodar na sua máquina (APK 3.10.0 com
você; só stdlib; nada é enviado à rede; não coloque o APK no repo):

```sh
python3 scripts/dex_scan_webview.py --apk WNM-3.10.0.apk          # relatório completo
python3 scripts/dex_scan_webview.py --apk WNM-3.10.0.apk --urls   # inclui assets .html/.js
```

Perguntas que o relatório precisa responder (numeradas para citarmos depois):

- **C1-1** — quais classes criam/possuem a WebView de cada fase (`WBootstrap`, `loadWeb`,
  `WarzoneDownloadActivity`), e qual **URL** cada uma chama (`loadUrl`/`file://`/`http://`/`https://`).
  Âncora nativa: o construtor de rotas `0x1f59078` produz
  `https://prod.cdni.callofduty.com/prelogin/web/index.html` **e**
  `bootstrap/index.html?env=%s&feature=prelogin|dailylogin|events|popup&semver=%s&l=%s`
  (`webview_localization`, `prod`, `sp_frontend`, `mp_frontend_mgl`) → a página *com ponte* é a
  `bootstrap/index.html`; a da tela de update é `prelogin/web/index.html`.
- **C1-2** — em quais classes/linhas há `addJavascriptInterface(...)` e com que **nome** o objeto é
  exposto (o `cod__`/`mcr` do `window`). Sem isso a página local não tem como chamar nada.
- **C1-3** — quais métodos têm `@JavascriptInterface`, em especial `passPreloginFence`,
  `CDNI_UseDevServer`/`CDNI_UseProdServer`, `saveKVP`, `closeWebView`; e se existe `CountDownLatch`/
  `wait()`/`synchronized` na classe que trata `passPreloginFence` (a única forma de a cerca ser um gate).
- **C1-4** — a página carregada **na fase de bootstrap** tem acesso à ponte, ou a ponte só é anexada em
  outra fase? (não assumir: existência da ponte ≠ acesso da página — você pediu explicitamente isso)
- **C1-5** — a tela de update usa `WebViewAssetLoader`/`shouldInterceptRequest`, ou rede do sistema?
  E o `WebView` tem `setJavaScriptEnabled(true)` **com** a interface anexada no mesmo objeto?

`scripts/dex_scan_webview.py` imprime: tabela de presença das chaves, por classe os métodos marcados com
`@JavascriptInterface` (leitura melhor-esforço de `annotations_directory_item`), todos os métodos de classes
candidatas, todas as strings que parecem URL/`.html`/`.js`/`.json`, as rotas `#/…` e os hosts
`*.callofduty.com`/`activision.com`. As duas seções finais são as que respondem C1-1/C1-4 e a questão
"`#/banned` existe no DEX?".

Sobre `#/banned` e `#/loading` (pergunta anterior): **no nativo não existe rota `#/banned`**; as rotas com
hash aparecem embutidas em formatos (`bootstrap/index.html?…&feature=popup&semver=%s#/kr-…`). `VERIFIED`:
a escolha de rota/hash é decisão da app web / do caller Java, não do `.so`.

## 8. Ponto de decisão da página (o "head" que você pediu)

`0x1f59078` (1002 instr) — um único chamador: **`0x1445f0c`** (3192 instr; strings

`0x1f411a8`, lendo `0xb8d63b8`/`0xb8d6bc0`).

| o que `0x1f59078` decide | evidência |
|---|---|
| tela de update vs página de bootstrap | `0x507c33` `https://prod.cdni.callofduty.com/prelogin/web/index.html` @`0x1f5951c` vs `0x4b9611`/`0x4bf764`/`0x4de009`/`0x5140b3` `bootstrap/index.html?env=%s&feature=prelogin…` |
| feature da página (`prelogin`, `popup`, `events`, `dailylogin`) | strings próprias; `popup` com sufixo `#/kr-` |

| mídia/ajuda (fora do prelogin) | `0x525cd9` `…/mgl-ui/media`, `0x55024b` `support.activision.com/au/en/warzone-mobile`, `0x555d36` `telescope.callofduty.com/ts-mobile/mgl/combat-record/liv…` |
| estado global usado | `0xba11c91`, `0xba11cb4`, `0xba13648` (região alta, não `.bss` da `.so`; escrita não atribuída) — `UNKNOWN` |

(`UNKNOWN`; provável config/KVX — `PROBABLE` por vizinhança com a família `0x143de14/0x14409d4`).

Rotas de bloqueio/erro vistas no nativo: `0x159f078` (popups de erro/mensagem/recuperável) e a tela de
shutdown é pilotada por `0x11d2d4c`/`0x11dc520` (`CDNIRestart` `0x4a604a`, xrefs `0x11d2d80`, `0x11dcdac`).
"Esperar update-check-meta" não aparece como espera explícita: o que existe é a máquina `0x15a1534` lendo
`cdni.meta` (m6.4) e o watchdog de 31 s do §4.

## 9. Consequências para o objetivo (não implementado aqui)

1. **Não perder tempo** tentando liberar a boot por `passPreloginFence`: a cerca é teardown/telemetria e já
   vence sozinha em ~31 s (`VERIFIED`). Qualquer plano que dependa de "fechar a tela" para o engine seguir
   está mal encadeado.
2. **A alavanca medida é dupla** e ambas são 100% HTTP local, sem TLS/pinning/TUN novos:
   (i) o JSON com `server_url`/`project_dir` que `0x157c3a8` consome (§6) e
   (ii) a resposta `use_dev_cdn` que o dispatcher aceita (§5). O passo seguinte da pesquisa é identificar o
   arquivo/origem do §6 (caminho, e se o launcher já intercepta esse host/caminho — `INTERCEPT_HOSTS` é
   `prod.cdni.callofduty.com`).
3. **Sem C1 não há página com ponte**: `bootstrap/index.html` é a página que os formatos nativos indicam,
   mas o `addJavascriptInterface` é Java. Se C1-2/C1-3 mostrarem que a ponte está anexada só na página de
   bootstrap (que o launcher hoje substitui por um placeholder de 1,4 KB sem JS), o caminho viável é servir
   uma página local que **chame os comandos reais** (`use_dev_cdn`, `proceed_anyway`, `saveKVP`) — não
   editar o `index.html` da tela de update (nada de bridge ali, `m6.5`).
4. `saveKVP` → `0x2bfd04c(obj,"game","kvps",key)` (`webviewdata.db`) é outro armazém do das respostas de
   popup (`tos`) — útil para observar *o que a página escreveu* sem mexer em nada (`VERIFIED`).

## 10. Limites

- Uma passada de `ADRP+ADD`/imediato só encontra acessos **com offset imediato**; campos acessados via
  `LDR [reg, reg]` (struturas com base em registro) ficaram de fora — é o caso de `0x567c458/460/470`
  (0 acessos no `flags`, mas 12 em `0x11d4a38` por outro método) e das flags `0xba11c91`/`0xba13648` (§8).
- Não há `.bss`/`.data` mapeado por símbolo aqui: "quem escreve" foi decidido por varredura de acessos, não
  por debug; valores em runtime não foram observados.
