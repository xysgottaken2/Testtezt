# M4.0 — Investigação: é possível pular a etapa “Verificando atualizações”?

> **Data:** 2026-10-04 (America/Sao_Paulo)  \
> **Base:** APK/XAPK 3.10.0.19854920 já analisado (M2/M2.2/M2.2.1) + verificação ao vivo de
> `cdni.meta` e da cadeia WebView em 2026-10-04  \
> **Pergunta do pedido:** o cliente pode ser levado a considerar a verificação de atualização concluída e
> avançar direto para o fluxo de assets/CDNI?  \
> **Regra:** análise estática + mocks locais; **sem** alterar certificado/pinning/trust, **sem** tocar
> autenticação, **sem** acessar serviço protegido da Activision, **sem** inventar endpoint/formato,
> **sem** brute force, **sem** APK/shard no Git.

---

## 1. Resumo executivo

**Veredito: `CANNOT_SKIP_DIRECTLY`** — não existe, na evidência disponível, um “atalho” que faça o cliente
considerar a atualização verificada. A etapa consome **bytes de um manifesto/arquivo**: os estados do
cliente (`MANIFEST_DOWNLOAD_ERROR`, `manifest_ver`, `cdni_indy_manifest_hash`, `num_files_manifest`,
`first_server_shard_idx`, `CDNI_MANDATORY_NOT_INSTALLED`) descrevem um **download + parse + casamento com o
estado local**, não um booleano “está atualizado” que se possa responder com `true`.

| Camada | Resposta | Nível |
|---|---|---|
| Existe flag/booleano “já atualizado” observável? | **Não encontrado em nenhuma evidência atual** (nenhum endpoint, campo ou string com essa semântica) | `UNKNOWN` (ausência de evidência) |
| Existe condição local do tipo `installed build >= required build`? | Existe o **dado** (`min_buildnum` no `cdni.meta` ao vivo) e o build instalado é **igual** a ele (`19854920`); a comparação no cliente é `HYPOTHESIS` | `PROBABLE` (dado) / `HYPOTHESIS` (uso) |
| `build-selector-102/103.js` ou `manifest.json` bastam para “estar atualizado”? | **Não.** O `103` é stub de shutdown; o `102` só escolhe o *bundle de UI de pré-login* pela faixa semver que o cliente informa. Nenhum dos dois valida build/atualidade | `VERIFIED` (corpo lido 2026-10-04) |
| O WebView de pré-login é o portão? | `HYPOTHESIS` — a cadeia WebView é servível localmente e **não contém** a validação de build | `HYPOTHESIS` |
| O que **é** necessário? | Servir a **cadeia mínima** (§6): meta/manifesto → comparação de build → manifesto de conteúdo → casamento local → (se faltar conteúdo) download | `HYPOTHESIS` com passos `VERIFIED` |

**A cadeia concreta que o cliente espera depois de “Verificando atualizações” está na §6.** O que falta para
fechar o veredito é **estático e está no APK**: onde cada símbolo da §3 aparece e qual é o caminho/URL do
primeiro fetch — a ferramenta `update-check-scan.py` (§8) responde isso e emite o veredito pela regra R1–R4.

> **O veredito não muda com “achismo”:** ele é `CANNOT_SKIP_DIRECTLY` porque o desenho observado (strings de
> download/parse + manifesto com hash e contagem de arquivos) **exige uma resposta**, e a única forma
> legítima de dar essa resposta é servi-la — o que é exatamente o objetivo do launcher.

## 3. Os símbolos do pedido — o que cada um indica

Classificação por **semântica do nome** (`HYPOTHESIS`) + o que precisa ser confirmado no APK. Nenhum foi
ainda localizado em binário nesta sessão (o APK do jogo não está no workspace do agente — ver §12).

| Símbolo | Categoria | O que indicaria | Confirmação necessária |
|---|---|---|---|
| `CDNI_100_PARSE_MANIFEST` | `estado_cdni` | código/estado do **parser de manifesto** de conteúdo dentro do cliente | arquivo (`libgame.so`? `classes*.dex`?) + call site |
| `ManifestOk` | `estado_cdni` | resultado **positivo** do parse → o cliente segue para o casamento com o conteúdo local | idem |
| `MANIFEST_DOWNLOAD_ERROR` | `estado_cdni` | houve **tentativa de download** do manifesto → a etapa é de rede, não local | idem |
| `CDNI_MANDATORY_NOT_INSTALLED` | `estado_cdni` | o cliente separa “build atual” de “**conteúdo obrigatório instalado**” | idem |
| `isCDNIFinished` | `estado_cdni` | flag consultada para considerar a etapa de conteúdo **concluída** | idem |
| `manifest_ver` | `manifesto` | **versão do manifesto** (local e/ou remoto) — base do casamento | idem |
| `cdni_indy_manifest_hash` | `manifesto` | **hash** do manifesto independente — nome/caminho/validação | idem |
| `first_server_shard_idx` | `manifesto` | **índice do primeiro shard** servido pelo CDN (estrutura de shards) | idem |
| `num_files_manifest` | `manifesto` | **nº de arquivos** do manifesto — completude da lista | idem |

Leitura conjunta (`PROBABLE`): o portão “Verificando atualizações” **não** é resolvido por um valor único; ele
é resolvido por um **manifesto** que lista arquivos/shards com versão e hash, comparado com o que já existe no
aparelho. É exatamente por isso que a resposta honesta hoje é `CANNOT_SKIP_DIRECTLY`.

## 4. O que já é `VERIFIED` (re-verificado em 2026-10-04)

### 4.1 `cdni.meta` (o único dado de versão mínima que temos)

`GET https://prod.cdni.callofduty.com/wzm/shard_cdn/android/_manifest/cdni.meta` → `200`, JSON:

```json
{
  "min_tu": 0,
  "min_buildnum": 19854920,
  "app_store_url": "https://play.google.com/store/apps/details?id=com.activision.callofduty.warzone",
  "#x3a74898c63cb5c55a": true, "#x3e9cc40e792dcfdcc": true, "#x3e93a69101751bfa8": false,
  "#x3b20ca17f00dfb4c9": false, "#x3c839f93c3b076242": true, "#x3bc57a21a42173b49": true,
  "#x377addea98016dad6": true
}
```

| Fato | Nível |
|---|---|
| O arquivo continua público, sem auth, ~320 B | `VERIFIED` (M2.2 2026-10-03; reconfirmado 2026-10-04) |
| `min_buildnum = 19854920` = build instalado `3.10.0.19854920` → **a condição “build >= mínimo” já é satisfeita hoje** | `VERIFIED` (valores) |
| `cdni.meta` **não contém** URL/hash de manifesto — só versão mínima, loja e flags opacas | `VERIFIED` (corpo inteiro acima) |
| O cliente compara `buildnum` local com `min_buildnum` para decidir update obrigatório | `HYPOTHESIS` (não observado em pcap; nenhum call site lido ainda) |
| As chaves `#x<hex>` são flags com nome ofuscado — **não** decodificadas | `UNKNOWN` |

### 4.2 Cadeia WebView (pré-login) — não é o portão de build

* `build-selector-103.js` → stub de shutdown que redireciona para `static/web/index.html`
  (“These servers are permanently offline.”). **Não há lógica de versão/build** — `VERIFIED` (M2.2,
  reconfirmado 2026-10-04).
* `build-selector-102.js` → **`VERIFIED` lendo o corpo em 2026-10-04**: lê `?semver=`, `?env=` e `?feature=` da
  URL do WebView, monta `manifestUrl = https://${env}.cdni.callofduty.com/manifest/manifest.json` (ou as
  variantes `popup`/`events`/`dailylogin`), filtra `builds` por `semver.satisfies(buildVersion, version.semver)`
  e injeta `<script>/<link>` apontando para o `root` escolhido; qualquer erro de `fetch` → `setOffline()`.
* `manifest.json` → `{"builds":[{"semver": "...", "root": "..."}, …]}`, com `>=3.10.0 <4.0.0 →
  `/prelogin/boot-15.0.0/` — `VERIFIED` (M2.2, reconfirmado 2026-10-04). O arquivo lista faixas **até
  `>=4.5.2 → boot-21.1.0`**, ou seja: é um seletor de **UI de pré-login** mantido por versão, não um
  validador de “posso avançar?”.

> **Resposta ao item 4 do pedido:** `build-selector-102/103.js` e `manifest.json` **não** contêm lógica
> suficiente para indicar a versão/build atual. Eles **recebem** o `semver` do cliente (parâmetro `?semver=`)
> e escolhem **UI de pré-login**. A validação de “posso avançar?” não está ali.

## 6. Cadeia concreta depois de “Verificando atualizações” (o entregável do pedido)

```
[P0] tráfego do WZM chega ao túnel  ──────────────── pré-requisito, ainda não observado (M3.4)
      │
[P1] fetch do meta/manifesto (candidato nº 1: cdni.meta)      ← VERIFIED que o arquivo existe e é público
      │        se falhar → estado de erro de download (MANIFEST_DOWNLOAD_ERROR)
      ▼
[P2] comparação de build: buildnum(local) × min_buildnum      ← HYPOTHESIS
      │        se build < mínimo → app_store_url (loja) → FORA DE ESCOPO
      ▼
[P3] download + parse do manifesto de conteúdo                ← HYPOTHESIS (URL/formato UNKNOWN)
      │        sucesso = ManifestOk / falha = MANIFEST_DOWNLOAD_ERROR
      │        campos esperados: manifest_ver, num_files_manifest, first_server_shard_idx,
      │                         cdni_indy_manifest_hash
      ▼
[P4] casamento com o estado local (manifesto/versão instalada, hashes, shards presentes)   ← HYPOTHESIS
      │
      ▼
[P5] se faltar conteúdo obrigatório → CDNI_MANDATORY_NOT_INSTALLED → fluxo de download/instalação
      │        (é a tela que queremos alcançar para descobrir quais shards/serviços servem)
      ▼
[P6] isCDNIFinished → o cliente segue para o próximo estágio (login/GVS/etc.)
```

**O que confirma cada passo (todas as confirmações vêm do scanner da §8):**

| Passo | Evidência que confirma | Onde olhar |
|---|---|---|
| P1 | string de caminho/URL junto de `cdni.meta`/`shard_cdn`/`_manifest/` **e** um call site que a consome antes da tela de conteúdo | `libgame.so`, `classes*.dex`, `assets/**` |
| P2 | `min_buildnum` (ou `buildnum`) em binário + comparação (`if_lt`/`cmp`) perto | `libgame.so` |
| P3 | `CDNI_100_PARSE_MANIFEST` + `MANIFEST_DOWNLOAD_ERROR` + `ManifestOk` no mesmo módulo; nome do arquivo do manifesto em string vizinha | `libgame.so` |
| P4 | `manifest_ver`, `cdni_indy_manifest_hash`, `num_files_manifest`, `first_server_shard_idx` | `libgame.so` |
| P5 | `CDNI_MANDATORY_NOT_INSTALLED` + strings de progresso/download | `libgame.so` / dex |
| P6 | `isCDNIFinished` e quem o consulta | `libgame.so` / dex |

> **Nada acima inventa endpoint.** O único endpoint concreto nomeado é `cdni.meta` (VERIFIED). Os demais
> caminhos **só entram na implementação depois** de saírem do APK com arquivo+offset (regra do projeto).

## 8. Ferramenta entregue: `update-check-scan.py`

```bash
# 1) Scan do XAPK + splits + OBB (tudo fora do repo; --apk é repetível)
python3 warzone-offline/tools/apk-analysis/update-check-scan.py \
  --apk /caminho/externo/base.apk \
  --apk /caminho/externo/split_asset_pack.apk \
  --dir /caminho/externo/obb-e-splits \
  --out /tmp/wzm/update-check.json

# 2) Ou sobre a árvore já decodificada
python3 warzone-offline/tools/apk-analysis/update-check-scan.py \
  --dir /tmp/wzm/apktool-output --out /tmp/wzm/update-check.json

# 3) Prova de que a ferramenta funciona (fixture sintética, sem APK real)
python3 warzone-offline/tools/apk-analysis/update-check-scan.py --self-test
```

O que ela produz, por símbolo: **encontrado/ausente**, arquivo, linha (texto) ou offset (binário) e
**confiança** (`VERIFIED` = texto/código legível; `PROBABLE` = sequência de bytes em binário). Contexto curto
de bytes só com `--context`, para depuração local — **nunca commitar** esse contexto.

**Regra do veredito (impressa no relatório):**

| Regra | Condição | Veredito |
|---|---|---|
| R1 | há indício de fetch (`cdni.meta`, `shard_cdn`, `_manifest/`) **ou** campo/estado de manifesto | `CANNOT_SKIP_DIRECTLY` — a etapa consome bytes |
| R2 | só há sinal de build/versão (`min_buildnum`, `force_update`, …) sem fetch/manifesto | `NEEDS_MORE_EVIDENCE` — achar de onde vem o valor comparado |
| R3 | nada encontrado | `NEEDS_MORE_EVIDENCE` — APK incompleto (split/OBB fora do scan) ou nomes mudaram |
| R4 | — | `CAN_SKIP_UPDATE_CHECK` **nunca** é automático: exige ler o trecho que conclui a etapa sem rede |

## 9. Se o scan responder `CAN_SKIP_UPDATE_CHECK` — especificação do mock mínimo (não implementado)

Condição para implementar: existir, no APK, um caminho que conclua a etapa **sem** rede (nenhum fetch entre o
início da tela e a conclusão) — ex.: o cliente só lê um estado local. Nesse caso o mock seria:

| Item | Especificação (a preencher com o que o APK mostrar) |
|---|---|
| Endpoint | **(a confirmar)** caminho exato extraído do APK — não inventar |
| Método | `GET` (a confirmar) |
| Resposta esperada | a estrutura lida pelo parser (`ManifestOk`) com os campos da §3 preenchidos |
| Campos necessários | `manifest_ver`, `num_files_manifest`, `first_server_shard_idx`, `cdni_indy_manifest_hash` (todos com o significado confirmado no código) |
| Evidência no código | arquivo + offset/linha do parser e do call site (saída do scanner) |
| Próximo endpoint solicitado | registrado pelo log do launcher depois de servir o mock (é o dado que fecha o ciclo) |

Nada disso é implementado nesta etapa — a especificação fica pronta para a iteração seguinte.

1. **P0 — ver o tráfego**: repetir o teste M3.4 com o WZM e confirmar que os pacotes do app chegam ao TUN

   a testar (se o cliente pedir esse arquivo, ele passa a receber um JSON válido em vez de placeholder).
3. **P3 — manifesto de conteúdo**: assim que o APK revelar o caminho do manifesto (strings + call sites),
   servir a estrutura correspondente com **apenas** o que o parser exige — sem inventar shard, sem inventar
   payload.
4. Cada passo é medido pelo log: qual foi o próximo request depois de cada resposta.

> **Nota de honestidade:** o passo 2 não garante nada por si — o cliente pode nunca pedir `cdni.meta` nesse
> fluxo (H1/H3). Ele é o teste mais barato e informativo **depois** de P0.
