## 2. D2 — confirmar `targetSdk` (o que rodar, e o que já se sabe)

```bash
# 1 comando, sem root, sem instalar nada. Também revela se o app é debuggable.
adb shell dumpsys package com.activision.callofduty.warzone \
  | grep -E "versionCode=|minSdk=|targetSdk=|flags=|privateFlags="
```

Linha esperada no formato do AOSP: `versionCode=1797 minSdk=29 targetSdk=34`.

| Campo | O que decide |
|---|---|
| `targetSdk=NN` | se `NN ≥ 24`, a regra `VERIFIED` do AOSP está satisfeita: **CAs de usuário não são lidas** sem opt-in de NSC ⇒ hipótese **A** se aplica |
| `flags=` sem `DEBUGGABLE` | fecha a única porta legítima restante, `<debug-overrides>` (exige `FLAG_DEBUGGABLE`) |
| `versionCode=1797` | amarra a medição ao build exato **3.10.0.19854920** (o do teste) |

Corroboração externa (secundária, **não substitui** o `dumpsys`): a listagem do **mesmo** build no APKMirror traz `Min: Android 10 (Q, API 29) · Target: Android 14 (API 34)` [APKMirror — COD Warzone Mobile 3.10.0.19854920](https://www.apkmirror.com/apk/activision-publishing-inc/call-of-duty-warzone-mobile/call-of-duty-warzone-mobile-3-10-0-19854920-release/call-of-duty-warzone-mobile-3-10-0-19854920-android-apk-download/). `PROBABLE` (dado derivado de manifesto por terceiro de confiança razoável); com `dumpsys` verde vira `DEVICE_OBSERVED`.
Registro de divergência honesta: outra listagem ([PGYER APKHUB](https://www.pgyer.com/apk/apk/com.activision.callofduty.warzone/download)) mostra `Target SDK Version 0` — metadado quebrado nessa fonte; **não** usado para nada.

## 3. D1 — logcat passivo durante as recusas

Ordem exata (o filtro só funciona se o buffer estiver sendo preenchido **durante** o lançamento):

```bash
PKG=com.activision.callofduty.warzone
adb logcat -c                                   # limpa o buffer
adb logcat -v threadtime > wzmtls.log &          # captura passiva (nada de -s: não sabemos a tag)
adb shell am force-stop $PKG                     # garante lançamento frio
# -> abra o WZM e espere as recusas TLS aparecerem no log do launcher (motivo=CLIENTE_RECUSOU_CERTIFICADO)
# -> quando as ~11 recusas se repetirem:
kill %1
grep -nE "Trust anchor for certification path|No subjectAltNames|Pin verification failed|Chain validation failed|X509Util|SSLHandshakeException|SSLPeerUnverifiedException|CertPathValidatorException" wzmtls.log
```

Se o filtro acima vier **vazio**, rode o captura-tudo antes de concluir qualquer coisa (o app pode não imprimir a exceção nessa trilha):

```bash
grep -nEi "ssl|tls|certif|handshake|okhttp|cdni" wzmtls.log | head -80
PID=$(adb shell pidof $PKG); adb logcat -d --pid="$PID" > wzm_pid.log; wc -l wzm_pid.log
```

### Tabela de decisão (strings exatas do AOSP; ver M6.1 §3.2)

| Mensagem que aparecer | Hipótese | Ação seguinte |
|---|---|---|
| `Trust anchor for certification path not found.` | **A** confirmada | a linha “TLS aceito sem root/sem patch” está fechada por política de confiança; redefinir objetivo |
| `No subjectAltNames on the certificate match` / `Hostname … not verified` | **B** | só então mexer no **certificado** (nomes), não na confiança |
| `Pin verification failed` / `X509Util: Failed to validate the certificate chain` | **C/E** | pinning real: servidor local nunca funcionará com este APK; registra e encerra |
| `Chain validation failed` + causa PKIX | defeito no **nosso** certificado | corrigir geração (`generate-local-cdni-cert.sh`) |
| Nada, e o servidor continua vendo 46 | inconclusivo | **parar** e reavaliar: ou o app não loga (D1 não decide), ou a recusa é silenciosa ⇒ fecha-se **E** estaticamente com `dex-scan.py` (D5 em M6.1 §6.5) |

## 7. D1 medido no aparelho (2026-10-07) — o que apareceu, o que isso decide, e o próximo experimento mínimo

### 7.1 Observação bruta (transcrição do log que você trouxe)

Processo observado: WZM, `uid 10692`, `pid 26799`. Três linhas, na ordem:

```
Pre-Engine: Meta Fetch Failed: failed to request url https://prod.cdni.callofduty.com/wzm/shard_cdn/android/_manifest/cdni.meta
cr_X509Util: Failed to validate the certificate chain, error: java.security.cert.CertPathValidatorException: Trust anchor for certification path not found.
javax.net.ssl.SSLHandshakeException: java.security.cert.CertPathValidatorException: Trust anchor for certification path not found.
```

`DEVICE_OBSERVED [RU]`. É transcrição da conversa, não dump de arquivo: se você tiver o log cru, vale colá-lo aqui para fixar timestamps/tag/pid por linha (N1 abaixo).

### 7.2 O que cada linha significa, com a fonte lida

| Linha | Emissor | Fonte |
|---|---|---|
| `Pre-Engine: Meta Fetch Failed: …` | `MetaFetchTask` (Java), ou seja **o fetch do `cdni.meta` é o que falha** — o pré-engine nem começa | `USER_SUPPLIED` (DEX) + `VERIFIED` (a URL no `.so`, `0x4e45b8`, único xref `0x25dc904`, função que **não** faz I/O — M6.3 §3) |
| `cr_X509Util: Failed to validate the certificate chain, error: …` | Chromium (`net/android/java/…/X509Util.java`; o prefixo `cr_` vem de `base/android/java/…/Log.java`: `LOGTAG_PREFIX + tag`). Falha **antes** do pinning: a validação de confiança da cadeia não achou âncora | `VERIFIED` (fonte lida em M6.1/esta rodada) |
| `javax.net.ssl.SSLHandshakeException: … Trust anchor …` | caminho `SSLSocket`/Conscrypt do `HttpURLConnection` (plataforma), **não** o curl nativo | `VERIFIED` (texto padrão do JSSE/Conscrypt) |

A mesma recusa aparece por **dois clientes distintos** (Chromium do WebView do prelogin e o `HttpURLConnection` do meta) porque ambos usam o store de âncoras do app, e o store de usuário só é consultado se `targetSdk <= 23` (`NetworkSecurityConfig.java`: "Applications targeting N and above must opt in into trusting the user added certificate store").

### 7.3 Veredito das hipóteses

| Hipótese | Estado | Base |
|---|---|---|
| **A** — o app não tem âncora de confiança para a CA do nosso servidor local | **CONFIRMADA** (`DEVICE_OBSERVED` + `VERIFIED`) | as duas últimas linhas acima; a expressão é exatamente o `NO_TRUSTED_ROOT` do Chromium e o `CertPathValidatorException` do JSSE |
| **B** — hostname/SAN não bate | **REFUTADA** | não apareceu `No subjectAltNames on the certificate match` nem `Hostname … not verified`; e o curl diria `SSL: no alternative certificate subject name matches target host name '%s'` (`0x55320f`) |
| **C** — pinning de certificado (NSC `pin-set`) | **REFUTADA** | nenhuma linha `Pin verification failed` |
| **D** — cadeia/validade/EKU do **nosso** certificado estabanados | **NÃO É A FALHA** | os portões `checkValidity()`/`verifyKeyUsage()` do Chromium rodam **antes** do trust manager e não reclamaram; a recusa é de âncora, não de forma |
| **E** — TrustManager customizado ignorando o store padrão | **refutada para os emissores observados** (o texto é dos emissores padrão do Chromium e do JSSE) | idem 7.2. Não confundir com o stack **nativo** do CDNI, que é outro cliente (M6.3 §7) |

### 7.4 O que **não** está provado (e não será afirmado)

O que está demonstrado é: tráfego para o **TUN** → servidor local escutando → **certificado recusado por falta de âncora**. **Nenhum MITM é reivindicado**: não medimos, e não precisamos medir, que o túnel intercepta — a recusa é do cliente antes de qualquer conteúdo.

Duas lacunas que impedem fechar isto como "só falta a âncora":

1. **N1** — atribuição por linha: os dois logs de recusa podem ser de **um** ou de **dois** clientes. Precisamos de tag/pid/timestamp do log cru para saber se o `cr_X509Util` veio do WebView (`pid 26799`) e em que instante em relação ao `SSLHandshakeException`.
2. **N2** — se, na hora de D1, havia ou não uma CA **do mesmo build** no store de usuário do aparelho é `UNKNOWN` para mim. Se havia, a recusa de âncora com `targetSdk=34` é exatamente o esperado (store de usuário fora do pool). Se não havia, D1 prova menos: só que o servidor local foi alcançado e o certificado não tinha âncora nenhuma.
