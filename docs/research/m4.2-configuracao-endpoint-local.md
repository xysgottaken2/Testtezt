## 2. O que as evidências dizem sobre endpoint e bootstrap

### 2.1. URL do bootstrap WebView

A evidência arquivada em [WZM 3.10 bootstrap](wzm-310-bootstrap.md) descreve:

```text
WZM 3.10.0 WebView
  → file:///android_asset/bootstrap/index.html
  → https://prod.cdni.callofduty.com/manifest/build-selector-103.js
  → https://prod.cdni.callofduty.com/static/web/index.html
```

- `MainActivity.loadWeb` carregando o asset e o pedido a `build-selector-103.js` foram registrados no material de WZM 3.10.0; a referência estática de `bootstrap/index.html` veio de outra build, 3.3.4. Não colapsar as duas versões.
- O `103` consultado serve atualmente um redirecionamento para a página de shutdown. Isso não é um seletor de servidor local nem uma configuração do launcher.
- A URL inicial usa o hostname/path `prod.cdni.callofduty.com/manifest/build-selector-103.js`; não foi documentado parâmetro de configuração para substituir o hostname/base URL nessa chamada.

**Confiança:** `WARZONE_VERIFIED` para a requisição WebView histórica da build e janela descritas; `VERIFIED` para o conteúdo atual do endpoint consultado. Isso não atribui um socket TCP do processo principal do jogo ao fluxo nem demonstra que o CDNI nativo de assets use a mesma implementação.

### 2.2. Selector legado `build-selector-102.js` e parâmetro `env`

O conteúdo remoto legado do `build-selector-102.js`, descrito em M2.2/M4.0, lê `?semver=`, `?env=` e `?feature=` e compõe URLs da forma:

```text
https://${env}.cdni.callofduty.com/manifest/manifest.json
```

Depois escolhe `builds[].root` por faixa SemVer para carregar a **UI WebView de pré-login**. Os manifests públicos observados retornam roots sob `prod.cdni.callofduty.com/prelogin/...`.

- O parâmetro `env` seleciona um prefixo de ambiente dentro do domínio `.cdni.callofduty.com`; não é um campo documentado que aceite uma URL/base host arbitrária nem aponta diretamente para um IP/servidor local.
- A presença desse JS legado não prova que a build WZM observada esteja usando `102`; o registro de bootstrap 3.10.0 nomeia `103`, que hoje redireciona para shutdown.
- A cadeia `manifest/manifest.json` é de seleção de UI WebView. Não é um catálogo de `.shard` nem prova o endpoint do CDNI nativo.

**Confiança:** `VERIFIED` para o comportamento do JS remoto legado conforme M2.2/M4.0; aplicação desse mecanismo à sessão WZM ou possibilidade de configurar `env` no cliente atual: `UNKNOWN`.

## 4. Existe resolver/DNS próprio ou configuração anterior ao socket?

### Observado

- O launcher lê `private_dns_mode`/`private_dns_specifier` como configuração do sistema; não altera Private DNS.
- Os logs históricos mencionam `dns.adguard.com`, mas sem owner UID do datagrama. Isso não demonstra que o WZM tenha emitido a consulta nem que use um resolver próprio.
- O pipeline local classifica DNS/TUN e responde apenas às perguntas CDNI reconhecidas; consultas restantes seguem pelo socket DNS protegido do **VpnService**.

### Não observado

- Nenhum código do WZM disponível mostra se ele chama o resolver Android, usa cache, IP literal, DoH/DoT próprio, `Network.bindSocket()` ou outra rede.
- Nenhum campo encontrado no código acessível permite trocar resolver, host, origem do manifest ou base URL do cliente.
- A ausência de referências no launcher não pode ser promovida a “o WZM não tem resolver/configuração própria”.

**Classificação:** resolver próprio do WZM = `UNKNOWN`; hostname/base URL CDNI nativa = `UNKNOWN`; parâmetro `env` do JS legado = `VERIFIED` somente no escopo de seleção da UI remota.

## 6. Veredito: TUN obrigatório?

- **Não há evidência de um endpoint local configurável diretamente no WZM.** `SEM_CONFIG_DIRETA_WZM` vale para o corpus disponível, não como afirmação universal sobre código ausente.
- **O único ponto anterior ao TCP implementado no Stable é a resposta DNS do `DnsResponder`, entregue pelo DNS virtual do `VpnService`/TUN.** Isso evita depender de conhecer IPs de Akamai, mas ainda depende da VPN e de a consulta chegar a ela.
- **O TUN não está provado como única alternativa teórica.** Um endpoint configurável dentro do WZM ou uma função de override não documentada poderia mudar a conclusão, mas não há como verificá-los sem o artefato. Redirecionamento do sistema/rede também não foi demonstrado e não resolve a confiança TLS por si só.
- **Próxima etapa indicada pelo pedido:** voltar ao `CONTROL_ONLY` e à investigação do TUN, validando primeiro um app com UID distinto. Em seguida, observar o WZM em sessão separada; não transferir resultado do controle positivo ao jogo.

### 6.1. Auditoria read-only para retomar `CONTROL_ONLY`

A revisão do código atual, após não encontrar rota direta, confirma que o controle positivo real **ainda não está implementado nem executado**:

- `CdnVpnService` recebe `EXTRA_WZM_PACKAGE` para `addAllowedApplication()`. Apesar do nome, é somente o pacote-alvo da sessão; não é endpoint. `CdnRouterController.startRouter(context, package)` aceita um pacote, mas `LauncherViewModel.startRouter()` chama sempre com `LauncherConfig.WZM_PACKAGE`; não há fluxo de UI `CONTROL_ONLY` para escolher/confirmar outro pacote.
- O `OwnerProbe` executado em `CdnRouterController` cria um listener efêmero em `127.0.0.1` e o cliente TCP é aberto pelo **próprio launcher**. O teste consulta ownership de uma tupla loopback e uma tupla inexistente; não verifica pacote de controle, SYN no TUN ou caminho per-app.
- `VpnCapturePlan` contém apenas `10.111.222.0/24`, sem rota default/IPv6 explícita. A allow-list de UID é um filtro separado; sua aceitação não demonstra que uma tupla real foi capturada.
- O caminho descrito em [M3.6 §8.1](m3.6-caminho-real-de-rede.md#81-controle-positivo-real-com-outro-app-planejado-nao-executado) segue como plano: sessão única com app de UID distinto, package/UID confirmados, só esse app na allow-list, conexão TCP local controlada e correlação da **mesma tupla** entre SYN no TUN, `getConnectionOwnerUid()` e accept do listener. Qualquer ausência/`INVALID_UID`/tupla divergente permanece inconclusiva.

Nenhum teste em device/app de controle foi executado nesta revisão; portanto não há resultado de controle positivo novo. O próximo trabalho pode ser desenho/teste de `CONTROL_ONLY`, mas não se deve alterar TLS/pinning, Private DNS, rotas IPv6, nem inferir causa para ausência de TCP/IPv6.
