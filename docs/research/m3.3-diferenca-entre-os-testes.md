**Data:** 2026-10-04 · **Device:** Samsung Galaxy S23 Ultra (Android 13/14), sem root · **WZM:** 3.10.0 (instalação externa, não distribuída)
**Escopo:** investigação + instrumentação. **Nesta fase NÃO se altera** roteamento, TLS, trust ou pinning — só se prova o que acontece por log.

## 2. Item 1 — o WZM pode usar DNS/endereços/cache diferentes depois da 1ª execução?

| Mecanismo | O que se sabe | Nível |
|---|---|---|
| Cache do resolvedor do Android (`netd`) | respeita o TTL da resposta; o cache Java (`InetAddress`) é de poucos segundos ([ctrl.blog, DNS TTL survey](https://www.ctrl.blog/entry/dns-client-ttl/)) | PROBABLE (fonte secundária) |
| Cache do Chromium/WebView (o WZM usa WebView para o bootstrap, M2) | ~60 s, até 1000 entradas, **ignora o TTL** | PROBABLE |
| Cache **da própria aplicação** (manifest/`cdni.meta`, pool de conexões HTTP/2, IPs fixados pelo jogo) | existe em qualquer app; não é observável de fora | HYPOTHESIS |
| **Private DNS (DoT)** configurado no sistema | consultas dos apps passam a ir para o resolvedor DoT (ex.: `dns.adguard.com`), **sobrepondo o DNS entregue pela VPN** (`addDnsServer`) — com VPN ativa isso quebra/contorna o DNS do túnel ([Privacy Guides](https://discuss.privacyguides.net/t/using-vpn-dns-on-android/32047), [hide.me](https://hide.me/en/blog/private-dns-on-android/)) | PROBABLE |
| Nossa resposta DNS para hosts CDNI | TTL de 30 s (`CdnRouterConfig.DNS_TTL_SECONDS`) | VERIFIED (código) |

**Leitura:** o "apenas consultas para `dns.adguard.com`" do teste B é exatamente o padrão esperado de um device com **Private DNS por hostname** — e o DNS do túnel (10.111.222.2) sendo ignorado explicaria `dnsIntercepted=0` **nos dois testes**. Alternativa igualmente compatível: o WZM resolve o CDNI por caminho próprio (DoH embutido/cache) e o túnel nunca vê a consulta. Distinguir as duas exige o log novo (§5) + a checagem do Private DNS (§7).

## 3. Item 2 — o processo está mesmo incluído na VPN per-app (nos dois testes)?

O que o código faz hoje: `builder.addAllowedApplication(com.activision.callofduty.warzone)` e, se o pacote não existir, `NameNotFoundException` → log de erro + encerramento (VERIFIED, `CdnVpnService.establish`).

O que **não** existia: nenhuma evidência no log sobre **quem** conectava. Agora existem três provas independentes:

1. **cabeçalho de sessão `[DIAG]`** — pacote alvo, versão, UID, se `addAllowedApplication` foi aceito e há quantas execuções o app roda (§5);
2. **`dono=uid=<n> (<pacote>)`** em cada tentativa de conexão aceita no listener, via `ConnectivityManager.getConnectionOwnerUid` (API 29+);
3. **`[DIAG] rede VPN: interface=... rotas=[...] dns=[...]`** — o que o sistema realmente aplicou (via `ConnectivityManager`/`LinkProperties`).

> Se o teste B for repetido e **nenhuma** conexão aparecer, o UID não é a explicação: será preciso olhar o cabeçalho (o app estava instalado? qual versão? o túnel era per-app?) e o vigia de inatividade (§5).

## 4. Itens 3 e 4 — rota `10.111.222.0/24`, bind direto e o mecanismo de bounce

* A VPN usa `addAddress(10.111.222.1/32)` + `addRoute(10.111.222.0/24)` + `addDnsServer(10.111.222.2)` (VERIFIED, `CdnRouterConfig`).
* Um pacote do app **dentro** da VPN para `10.111.222.1` é roteado para a interface `tun`. Dois desfechos possíveis, dependendo de qual tabela vence no kernel naquele aparelho (**UNKNOWN** — não é documentado):
  * a tabela `local` entrega direto ao kernel → o listener em `10.111.222.1:443` atende (caminho direto);
  * o pacote sai pelo `tun` → nosso leitor de TUN o **devolve** (bounce) para a pilha local, que tenta entregar a `10.111.222.1:443`.
* **Por que o bounce pode não completar:** se o bind em `10.111.222.1:443` falha com **EADDRNOTAVAIL**, o endereço não está atribuído/utilizável para sockets e **não existe listener** naquele endereço; um pacote devolvido para `10.111.222.1` fica sem dono. O caminho que sobra é o **loopback 127.0.0.1:443** — que só funciona se o cliente conectar **literalmente** em `127.0.0.1`.
* Consequência lógica: as 5 conexões do teste A só são compatíveis com um cliente que usou `127.0.0.1` **literal** (não com o valor `10.111.222.1` que nosso DNS devolveria). Isso é uma **hipótese em aberto** — daí a exigência de `dono=` no log.

Instrumentação nova (não altera o mecanismo):

* falha de bind ganha código estável: `motivo=ENDERECO_INDISPONIVEL` / `PORTA_EM_USO` / `PORTA_NEGADA` (`ListenerFailures.classify`, testado em JVM com errno real);
* quando o endereço do túnel não sobe, o log diz explicitamente: `SEM listener em 10.111.222.1:443: ... só o caminho 127.0.0.1:443 pode completar`;
* cada SYN devolvido ao TUN virou linha com contador: `(devolvido ao TUN -> listener HTTPS, bounce #N)`.

## 6. Hipóteses para a diferença A → B (com o que confirma/refuta cada uma)

| # | Hipótese | Confiança | Como o log novo decide |
|---|---|---|---|
| H1 | **Private DNS (DoT) ativo** nos dois testes: o DNS dos apps não passa por 10.111.222.2, logo `dnsIntercepted=0` e o app nunca recebe `10.111.222.1` | ALTA (HYPOTHESIS forte; casa com `dns.adguard.com` no teste B) | `[DNS] consulta DNS no túnel` mostra só nomes do sistema; `[DIAG] nenhuma consulta CDNI`; desligar Private DNS → deve aparecer a linha `[DNS CDNI recebido]` |
| H2 | **As 5 conexões do teste A não eram do WZM** (outro processo do aparelho alcançou 127.0.0.1:443) | MÉDIA | `dono=uid=…` nas conexões do próximo teste: se o UID não for o do WZM, H2 fica confirmada |
| H3 | No teste A o WZM usou **127.0.0.1 literal** (config/proxy/hosts anterior, ou resposta DNS antiga) e por isso o listener de loopback atendeu | MÉDIA | combinação de `dono=uid=<WZM>` + `via loopback` no próximo teste |
| H4 | No teste B o WZM **não fez requisições na janela do teste** (não estava em execução / ficou em tela inicial / cache sem rede) | MÉDIA | `[DIAG] nenhum pacote recebido no TUN` + `[DIAG] pacote alvo=… instalado=…`; repetir com o jogo em primeiro plano |
| H5 | O WZM resolve o CDNI por **DoH/cache próprio** e conecta direto no IP público (fora da rota 10.111.222.0/24) → o túnel não vê nada | MÉDIA | `dns-total` baixo/zero **e** `tunPackets=0` mesmo com o jogo ativo |
| H6 | `addAllowedApplication` não foi aplicado (serviço reiniciado pelo sistema sem o extra → túnel global, ou pacote alvo errado) | BAIXA/MÉDIA | `[DIAG] per-app: NÃO aplicado` ou `AVISO: sem pacote alvo`; e DNS de outros apps aparecendo no túnel |
| H7 | Contadores/objeto de log de **outra sessão** foram lidos (contadores zeram com o processo; arquivo rotaciona 256 KB/1000 linhas) | BAIXA | `[DIAG] sessão=#N` no `.txt` salvo + resumo final da sessão |

**Nada aqui é conclusivo antes de um teste novo no device com o APK instrumentado:** o objetivo desta etapa é tornar a diferença *observável*, não adivinhá-la.

## 7. Item 7 — protocolo de reprodução no device (para explicar A × B)

1. Instalar o APK novo (artifact `wzm-offline-launcher-debug`) e **não** limpar o log: `VER LOGS` → `SALVAR .TXT` antes de começar (guarda a sessão anterior).
2. Anotar/tirar print de: **Configurações → Rede → DNS privado** (se estiver por hostname, ex. `dns.adguard.com`, isso é o item 1 do teste) e de qualquer **proxy** configurado no Wi-Fi.
3. Launcher → iniciar roteador (HTTPS + túnel) → confirmar no log: `[DIAG] sessão=#…`, `per-app: o sistema aceitou addAllowedApplication(…)`, `listeners ativos=[…]`.
4. Abrir o WZM e ir até o ponto em que ele busca o bootstrap (tela de carregamento/rede).
5. Esperar ~2 min. O vigia escreve sozinho: ou as linhas de DNS/SYN, ou `[DIAG] nenhum pacote recebido no TUN…` / `[DIAG] nenhuma consulta DNS dos hosts CDNI…`.
6. `SALVAR .TXT` e comparar com o teste anterior. Repetir com **Private DNS desligado** (e, se possível, em outra rede) para separar H1/H5.
7. Só depois de identificar a causa, decidir se algo de arquitetura muda (nesta fase: nada muda).

Critérios de comparação rápida: `dns-total`, `dns-cdni-interceptado`, `pacotes`, `para-10.111.222.1`, `devolvidos-bounce`, `tcp-conexoes` e `dono=` de cada conexão.
