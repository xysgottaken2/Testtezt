# M3.2 — Investigação de TLS/trust/pinning no APK 3.10.0 (bloqueio de certificado)

**Data:** 2026-10-04
**Escopo:** descobrir como o cliente do WZM 3.10.0 configura TLS/trust/certificados e **se existe uma cadeia
de confiança suportável para uma implementação local legítima**; identificar se há pinning e onde é configurado.
**Regras desta investigação (não negociáveis):**

* ❌ Não modificar o APK do jogo (nem repack/repatch), não distribuir o APK, não commitar `.apk`/`.xapk`.
* ❌ Não implementar bypass de certificate pinning/trust, Frida, Xposed, root, `frida-server` etc.
* ✅ Somente leitura: inspeção estática **read-only** do artefato fornecido externamente + evidência de device.
* ✅ Toda conclusão vem com nível de evidência (VERIFIED / PROBABLE / HYPOTHESIS / UNKNOWN) e fonte.

## 0. Ponto de partida: evidência de device (2026-10-04, S23 Ultra) — WARZONE_VERIFIED

| Medida | Valor | Leitura |
|---|---|---|
| `tcpConnections` | **5** | o WZM abriu conexões TCP contra o servidor local |
| listener usado | **127.0.0.1:443** | chegou pelo **loopback**, não pelo endereço do túnel (`10.111.222.1`) |
| resultado do TLS | `SSLV3_ALERT_CERTIFICATE_UNKNOWN` (5/5) | o **cliente recusou a cadeia de certificados** — alerta emitido pelo cliente |
| `httpRequests` | 0 | nenhuma requisição HTTP completou (TLS não fechou) |

**Conclusão do M3 (routing):** o servidor local é alcançado pelo WZM. O que falta é **confiança TLS**.
O bloqueio agora é exclusivamente uma questão de *trust chain* — e é isso que este documento investiga.

### 1.1. Anomalia a explicar: `dnsIntercepted=0` com 5 conexões em `127.0.0.1:443`

Hipóteses (todas em aberto; nenhuma promovida):

| # | Hipótese | Como confirmar/refutar |
|---|---|---|
| H1 | O próprio app tenta endpoints em **loopback** (`127.0.0.1`) para o CDNI (caminho de desenvolvimento/cache local) | buscar literais `127.0.0.1`/`localhost`/`:443` no APK (o scanner faz isso) e ver o SNI/`Host` da primeira conexão no log |
| H2 | O app usou **DNS privado/DoH** ou cache de resolução (não passou pelo túnel) e o loopback veio de algum outro componente | log de DNS do túnel na próxima rodada (M3.2 adicionou registro das consultas **encaminhadas**) |
| H3 | As conexões partiram de um **WebView** com URL/host já resolvido em cache de sessão anterior (quando o DNS foi interceptado) | limpar dados do app/WebView e repetir; observar `dnsIntercepted` |
| H4 | As 5 conexões não vieram do WZM | comparar com o log completo e, se possível, `adb shell ss -tnp` durante a tentativa |

O que já foi feito para a próxima rodada: o launcher agora registra (i) cada conexão TCP com a marca
`via loopback` / `via túnel` e (ii) as consultas DNS **encaminhadas** (uma vez por nome), então
`dnsIntercepted=0` não ficará mais sem contexto.

## 2. O que precisa ser respondido no APK 3.10.0

1. O `AndroidManifest.xml` declara `android:networkSecurityConfig`? E `usesCleartextTraffic`?
2. Existe `res/xml/network_security_config.xml`? Quais *trust anchors* (`system`? `user`? CA embutida via
   `<certificates src="@raw/..."/>`)? Há `<pin-set>` (pinning declarativo)?
3. Existe **bundle de CA embutido** (`assets/`, `res/raw/`, `.bks`/`.p12`) ou *trust store* própria?
4. Há APIs de pinning no código: `okhttp3.CertificatePinner`, TrustKit (`com.datatheorem`), pinning
   próprio (`checkServerTrusted` customizado), `sha256/` (SPKI pins)?
5. Qual stack fala com o CDNI: `okhttp`, `HttpsURLConnection`/Volley, Cronet, **WebView** ou nativo
   (`libssl`/BoringSSL dentro de `.so`)? — isso decide se o NSC se aplica.
6. Existem literais de loopback (`127.0.0.1`, `localhost`) ligados ao bootstrap (confirma H1)?

### 2.1. Por que (5) é decisivo — VERIFIED por documentação

* O **Network Security Configuration** vale para o tráfego gerenciado pelo framework, **incluindo WebView**
  e `HttpsURLConnection` (OWASP MASTG-KNOW-0015; doc Android).
* Para **código nativo**, o NSC **não se aplica** — stacks próprias (BoringSSL/mbedTLS em `.so`) trazem
  seus próprios roots/pins (mesma fonte).
* App com `targetSdk ≥ 24` **não confia em CA instalada pelo usuário** por padrão; confiar exigiria
  `<certificates src="user"/>` explícito no NSC (doc Android "Network security configuration").
* Portanto: se o CDNI for WebView/HttpsURLConnection e **não** houver pinning e o NSC permitir `user`
  (ou não houver NSC), a CA local de usuário **poderia** ser uma cadeia legítima. Em qualquer outro caso,
  não há caminho sem root ou sem alterar o app — o que está fora de escopo por decisão do projeto.

## 3. Ferramenta pronta (read-only) — `tls-trust-scan.py`

`warzone-offline/tools/apk-analysis/tls-trust-scan.py` varre o artefato **sem modificar nada** e emite um
relatório (console + JSON) com: manifest/NSC, trust anchors, pin-set, certificados embutidos, assinaturas de
pinning/stacks TLS, referências a loopback e a hosts CDNI, e uma **matriz de decisão** de cadeia de confiança.

```bash
# self-test (roda no CI, fixture sintética — 14 verificações)
python3 warzone-offline/tools/apk-analysis/tls-trust-scan.py --self-test

# APK/XAPK completo (ZIP, sem extrair)
python3 warzone-offline/tools/apk-analysis/tls-trust-scan.py \
  --apk /caminho/externo/warzone-3.10.0.19854920.xapk \
  --out /tmp/wzm-tls-trust.json

# melhor cenário: APK já decodificado (apktool/jadx) — aí o NSC sai como VERIFIED (texto)
python3 warzone-offline/tools/apk-analysis/tls-trust-scan.py \
  --dir /caminho/externo/apktool-out \
  --out /tmp/wzm-tls-trust.json
```

O relatório **não** deve ir para o repositório inteiro: copie apenas o resumo redigido (§5) e o JSON pequeno,
se quiser versionar a evidência.

## 4. Matriz de decisão — cadeias de confiança possíveis

| Opção | Status | Observação |
|---|---|---|
| CA local no armazenamento do **usuário** (sem root) | **VIAVEL somente se** o APK aceitar `src="user"` (ou não tiver NSC) **e** não houver pinning para os hosts CDNI | é a única opção sem root/no APK change; depende do resultado do scanner |
| CA local no **system store** | **FORA DE ESCOPO** | exige root/`adb root`/imagem de sistema — contraria a restrição de projeto |
| Alterar trust/pinning do app (patch/repack/replace de pins) | **PROIBIDO** | decisão explícita do usuário; também implica distribuir APK modificado |
| Caminho **loopback previsto pelo próprio app** (H1) | **UNKNOWN** | se existir, ainda precisa passar pelo trust; o scanner busca os literais |
| Usar o CDNI **real** (internet, hosts oficiais) | fora do objetivo (preservação offline) | não é o problema que estamos resolvendo |

**Leitura do bloqueio atual (VERIFIED no device):** o cliente recusou a cadeia local
(`certificate_unknown`), o que é exatamente o comportamento esperado de um app `targetSdk ≥ 24` sem
`src="user"` e/ou com pinning. A pergunta que o scanner responde é **qual dos dois** é o caso — e, se for
apenas o armazenamento (sem pinning), se existe algum caminho legítimo.

## 6. Critérios de decisão (o que fazer com o resultado)

| Resultado do scanner | Consequência para o projeto |
|---|---|
| NSC com `src="user"` e **sem pinning** para o CDNI | implementar UI/instalação guiada da CA local no device (o usuário instala manualmente) e testar — **cadeia legítima, sem root, sem tocar no APK** |
| NSC `system`-only, **sem pinning** | documentar como **BLOQUEADO sem root**; registrar o caminho alternativo (patch do app) como fora de escopo |
| Pinning presente (NSC `pin-set` ou biblioteca/`.so`) | **BLOQUEADO**; documentar exatamente onde o pin está configurado (§5) e encerrar a linha de investigação sem bypass |
| Cliente CDNI nativo (`.so` com BoringSSL/roots próprios) | pinning/roots fora do alcance do NSC → tratar como **bloqueado**, salvo se o scanner mostrar o contrário |

Em qualquer cenário, o launcher continua sendo útil: ele **prova** que o tráfego chega ao servidor local,
registra os paths exatos e mantém a evidência no `RequestLog` (tela VER LOGS).
