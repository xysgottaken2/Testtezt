# M4.1 — Dono das conexões: por que `127.0.0.1:443` não pode ser atribuído por dedução

> **Data:** 2026-10-04 (America/Sao_Paulo) \
> **Contexto:** o M3.6 fechou a instrumentação do TUN (IPv4/IPv6, TCP/UDP/ICMP, DoT, DoH, contabilidade
> por UID) e o quadro de afirmações. Ficou um buraco explícito: as conexões que aparecem no listener de
> **loopback** (`127.0.0.1:443`) recebiam `dono=NAO_RESOLVIDO (INVALID_UID)` no log e o quadro não
> conseguia dizer **quem** as abriu — nem se a leitura antiga ("não é do jogo") era sequer legítima. \
> **Objetivo:** responder "de quem é essa conexão?" com evidência e **nível de confiança**, sem tocar em
> pinning, autenticação, anti-cheat, certificados ou endpoints. \
> **Regra da etapa:** `INVALID_UID` **não** é prova de nada; teste sintético **não** é evidência do WZM.

Marcador para o `check-docs.sh`: `INVALID_UID_NAO_PROVA`.

## 1. O que a API pública realmente significa

| Fato | Fonte | EVIDENCE | CONFIDENCE |
|---|---|---|---|
| `ConnectivityManager.getConnectionOwnerUid(protocol, local, remote)` existe desde a **API 29** e devolve o uid do **socket** dono da tupla, via netlink `inet_diag`/`sock_diag` | AOSP `frameworks/base` commit `0ac2c0945b00d7716319bc5aa86ce0b249f14cea` ("Add ConnectivityManager.getConnectionOwnerUid()", bugs 9496886/109758967) | VERIFIED | alta |
| A chamada exige ser a **VPN ativa** (ou ter `NETWORK_STACK`): `enforceActiveVpnOrNetworkStackPermission()`; fora disso → `SecurityException` | mesmo commit | VERIFIED | alta |
| `ConnectivityService.getConnectionOwnerUid` faz `if (vpn != null && !vpn.appliesToUid(uid)) return INVALID_UID;` | mesmo commit | VERIFIED | alta |
| Só TCP e UDP; outro protocolo → `IllegalArgumentException` | mesmo commit | VERIFIED | alta |
| `INVALID_UID` (`Process.INVALID_UID` = `-1`) significa **duas** coisas distintas: (a) a conexão **não está** na tabela; (b) a conexão existe, mas o uid dono **está fora** da VPN que chamou | consequência direta do filtro acima | VERIFIED | alta |
| Um caso conhecido de "socket existe e não é encontrado": TCP com `SO_BINDTODEVICE` preso a `tun0` (kernel ≥ 5.7) — a consulta vai com `ifIndex = 0` e não casa | estudo de caso público `Oleglog/OlConnect#5` (2026-10-01) | HYPOTHESIS | média |

**A consequência que muda a leitura do log:** com allowlist estrita (só o WZM dentro da VPN), a API
responde `INVALID_UID` para **tudo** que não pertence ao WZM — inclusive para o **próprio launcher** e
para o listener local. Então:

| Retorno da API | O que **é** legítimo concluir | O que **não** é |
|---|---|---|
| uid resolvido (`!= -1`) | aquele uid **está coberto pela VPN** ⇒ autoria **comprovada** (evidência de autorização) | — (nada a ressalvar; só o uid é "prova") |
| `INVALID_UID` | "não deu para atribuir", com duas causas possíveis (ausente × fora da VPN) | "não é do jogo", "é de outro app" |
| `SecurityException` | quem chamou não é o VPN ativo ⇒ resultado **inconclusivo** | "não é do jogo" |
| API antiga / endereços indisponíveis / argumento inválido | consulta indisponível | qualquer conclusão |

`INVALID_UID_NAO_PROVA` — é exatamente por isso que `ConnectionOwnership` tem **seis**
`Outcome` separados e nunca um `Boolean`.

## 3. Por que o loopback não pode ser "medido" pelo túnel

O tráfego para `127.0.0.1` é entregue pela própria pilha local (`local` table, prioridade 0): **não
passa** pelo `tun`, **não** aparece na contabilidade do UID pelo túnel e **não** é restringido pela VPN
per-app (`addAllowedApplication` limita o uso da VPN, não o acesso ao loopback). Além disso o listener é
alcançável por **qualquer** app do aparelho, com ou sem a VPN ligada.

Duas hipóteses estruturais que a instrumentação tinha de deixar separadas:

* **H5 — DNS privado/DoT (porta 853)**: o `TunPolicy` só trata **UDP:53**; DoT é *system-wide*, sai pela
  rede física e **não** pode ser interceptado pelo TUN. Se o cliente resolve o CDNI por DoT, a consulta
  nunca chega ao DNS virtual — e nenhuma resposta "manda" o cliente ao loopback.
* **H7 — socket nativo/`SO_BINDTODEVICE`**: se um socket do jogo estiver preso a `tun0`, a consulta de
  autoria pode devolver `INVALID_UID` **mesmo com o socket existindo** (o `sock_diag` vai com
  `ifIndex = 0`).

Nenhuma das duas é causa; as duas são razões para **não** tratar `INVALID_UID` como resposta.

## 4. O teste de controle (e como lê-lo)

`OwnerProbe.run(...)` executa, em ordem, com sockets de verdade **locais** (nada sai do aparelho):

| Passo | O que faz | O que o resultado significa |
|---|---|---|
| `loopback_proprio` | conecta no próprio listener (`127.0.0.1:<porta>`) e consulta a autoria | se resolver uid → a API funciona e prova autoria; se `INVALID_UID` → confirma o filtro `appliesToUid` no device |
| `tunel_proprio` | conecta em `10.111.222.1:443` (loopback do `tun`) | mesma leitura, agora no endereço do túnel |
| `tupla_inexistente` | consulta `TCP 127.0.0.1:1 → 127.0.0.1:1` **sem** abrir socket | separa "não encontrado" de "fora da VPN" (empiricamente os dois podem coincidir; o teste registra isso em vez de esconder) |
| `escopo_da_vpn` | passo declarativo | registra em voz alta que a allowlist cobre só o alvo |

Leitura automática (`Report.expectation()`), sempre em uma destas quatro frases — nunca "é/não é do
jogo":

* `SEM_PERMISSAO` → *inconclusivo* (o serviço não é o VPN ativo naquele instante);
* algum resolvido → a API **prova** autoria para uid coberto pela VPN;
* `INVALID_UID` → confirma a ambiguidade (inclusive para a conexão do **próprio** launcher);
* nada útil → `UNKNOWN` explícito.

* nada de pinning, autenticação, anti-cheat, Frida, root, patch ou repack;
* nenhum payload, corpo HTTP, cookie, token ou credencial é registrado (só metadado de cabeçalho);
* o listener segue **loopback + endereço do túnel** (nunca `0.0.0.0`);
* conexão no loopback **não** conta como evidência de tráfego do WZM — só uid resolvido conta;

  inexistente não abre socket.
