## 3. Per-app, destino e seleção de rede — controles diferentes

### 3.1 Allow-list não é lista de todos os destinos capturados

- **`VERIFIED` — Android:** `VpnService.Builder.addAllowedApplication()` seleciona quais aplicações podem usar a VPN. Aplicações fora da allow-list usam a rede como se a VPN não estivesse em execução. A API separa isso de `addRoute()`.
- **`VERIFIED` — Android:** `addRoute()` instala uma rota para destinos; a documentação diz que rotas filtram por endereço de destino, aceita IPv4/IPv6 e usa prefixo mais longo quando rotas se sobrepõem.
- **`VERIFIED` — código deste repositório:** `CdnVpnService` consome `VpnCapturePlan.routes`, atualmente somente `10.111.222.0/24`; não chama `addRoute("0.0.0.0", 0)`, `addRoute("::", 0)` nem adiciona prefixo IPv6. A allow-list per-app é configurada separadamente.
- **`VERIFIED` — limite da afirmação:** isso comprova o plano que o launcher passa ao `Builder`, não o encaminhamento final de uma conexão WZM específica. Não se deve afirmar que um destino externo “saiu pela rede física” sem observar esse fluxo.
- **`UNKNOWN` — Warzone:** o IP/porta de destino TCP que o WZM tentou na janela histórica não foi observado. Portanto, não se sabe se o destino casaria com `10.111.222.0/24`.

### 3.2 `Network.bindSocket()` e `VpnService.protect()`

- **`VERIFIED` — Android:** `Network.bindSocket(socket)` associa aquele socket a um `Network` escolhido; a documentação diz que os dados do socket usam essa rede mesmo se o processo tiver outro vínculo de rede.
- **`VERIFIED` — Android:** o caminho documentado para uma VPN permitir que apps escolham uma rede para contornar a VPN depende de `VpnService.Builder.allowBypass()`. Sem `allowBypass()`, apps não podem simplesmente contornar a VPN; um app que fixe socket/processo a uma rede pode ficar sem conexão quando o bypass não é permitido.
- **`VERIFIED` — código:** o serviço deste repositório não chama `allowBypass()`.
- **`UNKNOWN` — Warzone:** não foi observado WZM chamando `Network.bindSocket()`, `bindProcessToNetwork()` ou usando outro `Network`. A API explica uma possibilidade de seleção de transporte; não prova uso pelo jogo.
- **`VERIFIED` — escopo de `protect()`:** `VpnService.protect()` protege sockets do próprio serviço VPN contra recirculação pelo túnel. Não é uma explicação demonstrada para sockets do WZM nem um método disponível ao launcher para consultar sockets de outro app.

**Conclusão:** destino fora do prefixo explícito, seleção explícita de `Network`, socket sem socket TCP consultável no instante da consulta, cache/resolver próprio e fluxo sem atividade na janela são possibilidades diferentes. Nenhuma foi escolhida como causa por exclusão.

## 4. `getConnectionOwnerUid()` — UID, `INVALID_UID` e orientação da tupla

### Semântica verificada

- **`VERIFIED` — API pública (API 29+):** `ConnectivityManager.getConnectionOwnerUid(protocol, local, remote)` aceita TCP ou UDP e retorna um **UID** quando a conexão é encontrada e o chamador pode observá-la; a API pode retornar `Process.INVALID_UID` (`-1`). O chamador precisa ser o VPN ativo ou ter `NETWORK_STACK`.
- **Limite UDP (AOSP de referência):** a mudança original descreve TCP com endpoints local/remoto e UDP com endpoints ou só origem; o código AOSP também faz lookup UDP exato e, se não achar, tenta por endereço/porta local. Logo um UID resolvido em consulta UDP não deve ser tratado como prova independente de correspondência do endpoint remoto. A instrumentação de caminho abaixo conta como atribuição forte apenas o TCP SYN/tupla que o pipeline já consulta.
- **`VERIFIED` — AOSP (referência de implementação):** a mudança que introduziu a API explica que o objetivo era substituir acesso direto de apps a `/proc/net/{tcp,tcp6,udp,udp6}`. A implementação usa `inet_diag`/`sock_diag`; a implementação AOSP consultada também filtra UID via `vpn.appliesToUid(uid)`. Em consequência, `INVALID_UID` pode cobrir tupla ausente **ou** owner fora do escopo da VPN ativa. Isso descreve AOSP, não substitui medição da versão/OEM do aparelho.
- **`VERIFIED` — limite:** a função devolve UID; não devolve PID, nome de processo nem qual processo dentro de um pacote abriu o socket. Converter UID em `getPackagesForUid()` produz pacote(s), não PID.
- **`VERIFIED` — ambiguidade:** `INVALID_UID` significa “não encontrado **ou** não permitido/fora do escopo visível”. Não significa “WZM”, “não WZM” nem “outro app”. O momento da consulta também importa: socket ausente/fechado ou tupla não correspondente permanece sem atribuição.

### Para um socket retornado por `ServerSocket.accept()`

O socket aceito é visto do lado do servidor. Para perguntar pelo UID do peer cliente, a consulta deve ser:

```text
local da consulta  = accepted.remoteSocketAddress  // endereço/porta do cliente
remote da consulta = accepted.localSocketAddress   // endereço/porta do listener
```

O AOSP grava os campos locais como origem e os remotos como destino na consulta de socket. Tentar também a orientação invertida como fallback não é seguro: pode identificar o socket do servidor em vez do cliente. `ConnectionOwnershipTest` agora inclui um par TCP loopback real que fixa a direção do peer. Esse é um teste de tupla/sockets JVM; não substitui a prova on-device de que a API Android resolve o UID esperado.

### PID/processo sem root

- **`VERIFIED` — processo próprio:** `Process.myPid()` devolve o PID do processo chamador. O launcher registra a tupla completa dos sockets que ele próprio abre e o PID próprio no momento do registro. O peer aceito só recebe esse PID quando a tupla completa (endereço/porta local e remota) casa com uma entrada recente e de uso único. Uma porta efêmera isolada continua sendo apenas `PROBABLE`.
- **`VERIFIED` — outros processos:** a referência oficial classifica `ActivityManager.getRunningAppProcesses()` como API de debugging/UI informativa; ela não é uma garantia de inventário cross-app completo nem de mapeamento socket → PID. A visibilidade pode ser filtrada por versão/política do sistema. Uma lista vazia não prova que o WZM não esteja rodando. `TrafficStats` mede bytes/pacotes por UID, não associa um socket arbitrário a PID. Android 10+ restringe acesso de apps a `/proc/net`.
- **Conclusão limitada:** entre as APIs públicas Android revisadas não há um mapeamento genérico socket arbitrário → PID para um app comum sem root/privilégios. Uma consulta que resolve o UID do WZM ainda agrupa processos que compartilham esse UID; não separa processo principal de helper. `PackageManager` pode revelar nomes de processos declarados no manifesto, mas isso é inventário estático, não prova de execução.
- **`UNKNOWN`:** PID/processo de quem abriu as cinco conexões históricas não pode ser recuperado retroativamente pelo novo registro de tupla.

## 5. `127.0.0.1` — o que significa e o que não revela

- **`VERIFIED` — endereço:** Android/Java documenta o bloco `127.*.*.*` como loopback: os pacotes retornam à pilha local. O peer visto por um listener pode ser `127.0.0.1` para processos diferentes do mesmo perfil; o endereço não inclui UID/PID.
- **`PROBABLE` — compartilhamento entre apps:** um reporte público da Amnezia VPN para Android 15 em Galaxy S25 descreve Termux, excluído da VPN per-app, conectando a um SOCKS5 em `127.0.0.1:10808`; PR associado propõe autenticação no listener. É um caso reportado e uma correção proposta, não documentação normativa nem reprodução independente nossa. Torna acesso cruzado um caminho plausível, mas não identifica o autor deste listener nem prova que Warzone o usou. AOSP `netd` também contém regras de roteamento local/loopback; a tabela exata pode variar por versão/OEM.
- **Relatos sobre owner lookup (não normativos):** sing-box #4009 descreve, em Android 16, falhas reportadas de `getConnectionOwnerUid()` para sockets ligados a interface e atribui isso a uma diferença `idiag_if`; é explicação do relator, não conclusão verificada aqui. Amnezia PR #3199 usa a API no split tunneling estrito e documenta casos de `INVALID_UID`; trata-se de PR/implementação de terceiros e os testes declarados são específicos daquele projeto/device. Husi #982 foi revisado, mas **descartado como evidência**: o próprio projeto rotulou o issue como inválido/AI slop, e o autor informou que a descrição foi redigida por agente sem logs completos.
- **Limite de transferência:** nenhuma dessas fontes públicas é evidência do WZM, deste launcher ou do Galaxy S23. Sockets ligados a interface, `INVALID_UID` e cross-app loopback são apenas pistas para desenhar instrumentação segura.
- **Caveat de versão (`VERIFIED`):** Android 17 adiciona restrições de loopback **entre perfis**. Isso não deve ser aplicado retroativamente ao Galaxy S23 documentado com Android 13/14 nem confundido com isolamento entre apps no mesmo perfil.
- **Regra desta investigação:** toda conexão a `127.0.0.1:443` permanece diagnóstico secundário. Mesmo que a API resolva o UID-alvo para a conexão local, isso prova apenas que aquele UID abriu aquela conexão local; não prova tráfego externo, CDNI, DNS do WZM ou passagem pelo TUN.

### Marcador de lançamento

`markWzmStarted` registra quando a chamada de lançamento do launcher retorna. Ele é um marcador temporal, não um callback de processo do Android. Portanto:

```text
antes do marcador  ≠ prova de que o WZM não abriu a conexão
após o marcador   ≠ prova de que o WZM abriu a conexão
UID resolvido     = UID desta conexão local, não tráfego externo
```

## 6. DNS, Private DNS, DoT, DoH e outros caminhos

- **`WARZONE_VERIFIED` — configuração histórica:** `private_dns_mode=hostname`, `private_dns_specifier=dns.adguard.com` foi reportado no device.
- **`VERIFIED` — Android:** Private DNS do sistema pode usar DoT; documentação Android recomenda que apps com resolvedor próprio respeitem as APIs/configuração Private DNS ou usem o resolver do sistema.
- **`WARZONE_VERIFIED` — log histórico:** o túnel registrou duas consultas UDP DNS de `dns.adguard.com`; não há atribuição de UID/processo que prove que foram do WZM.
- **`UNKNOWN` — caminho do WZM:** não sabemos se o WZM usa o resolver Android, DNS em cache, IP fixo, resolver próprio, DoH/QUIC, outra rede ou nenhum pedido durante a janela observada.
- **`VERIFIED` — limite do classificador:** UDP/53 é observação de porta/protocolo DNS; TCP/853 é candidato a DoT; UDP/443 é candidato QUIC/DoH. Porta isolada não prova protocolo criptografado ou identidade do processo. A ausência de uma dessas portas no TUN não prova ausência desse mecanismo fora do TUN.
- **Restrição mantida:** Private DNS fica habilitado. Nenhuma tentativa pede para desligá-lo. TLS, pinning, certificados, autenticação e APK do WZM permanecem intocados.

## 7. Atualizações implementadas no código M4.1

1. `SelfPorts` preserva a tupla cliente completa e, em sockets registrados pelo launcher, o `Process.myPid()` do próprio processo; match tem TTL de 30 s e é consumido uma vez. O cliente registra logo após `connect()` retornar, pois só então conhece a tupla local completa: o listener pode vencer essa corrida. Nesse caso a checagem única degrada para faixa efêmera `PROBABLE`/`INDETERMINADO`, nunca para `VERIFIED`; a tupla aceita sem registro fica marcada por TTL e qualquer registro tardio da mesma tupla é recusado, sem promoção retroativa nem entrada exata pendente. A faixa é apenas pista compartilhada.
2. `ConnectionOwnership.peerTupleForAcceptedSocket()` explicita a inversão peer → listener; não consulta orientações alternativas. Erros de API, falta de permissão, `INVALID_UID`, API antiga e tupla ausente ficam em estados distintos.
3. O `LocalHttpsServer` faz **uma única consulta** por socket aceito e passa o mesmo resultado estruturado ao veredito de origem; evita duas consultas potencialmente divergentes à tupla e mantém UID distinto de PID/processo. Os dois caminhos (`startRouter` e `startHttps`) usam a mesma fábrica/configuração de callbacks, mas não têm o mesmo ciclo de vida: `startRouter` define o pacote-alvo, sobe a VPN e cria o servidor em thread após o endereço TUN; depois da tentativa do servidor, executa o probe TCP efêmero. `startHttps` é síncrono/diagnóstico: não inicia a VPN nem roda o probe e pode não ter `targetPackage`/`targetUid` se não houve `startRouter`. Portanto, callbacks compartilhados não tornam `startHttps` evidência do caminho WZM/TUN; isto é revisão estática, não observação no device.
4. O veredito de loopback distingue tupla própria registrada pelo launcher, UID do launcher, UID do alvo, outro UID, possível launcher e indeterminado; preserva também o motivo de falha/`INVALID_UID`. UID do alvo em loopback não promove evidência de tráfego externo do jogo.
5. O teste de controle roda em listener TCP efêmero próprio ligado somente a `127.0.0.1`; não conecta ao HTTPS de produção, não dispara handshake TLS/contadores, não testa o TUN e não sai para a rede. Mede apenas uma tupla aberta pelo launcher e uma tupla intencionalmente inexistente; nenhum resultado é extrapolado ao WZM.
6. O contador `tunUidVerifiedFlows` só incrementa quando `getConnectionOwnerUid()` retorna o UID-alvo da sessão para o SYN observado no TUN, não qualquer UID resolvido. O log diz que UID não identifica PID/processo.
7. O quadro de evidências não promove pacote sem UID no TUN, consulta DNS sem UID, porta candidata DoH/DoT, socket de controle, loopback isolado ou silêncio a “tráfego do WZM”/causa. Antes/depois do marcador continua mera correlação.
8. Nenhuma nova execução do WZM ou observação do device ocorreu nesta revisão; atribuição e caminho de rede reais continuam `UNKNOWN` até uma sessão atribuível no aparelho.
9. Auditoria estática dos `when` Kotlin: dispatches de `ConnectionOwnership.Outcome`, `LoopbackOrigin.Verdict`, fases do roteador, `PacketParse`, `IpVersion`, `TunAction`, categorias IPv6, `TunObservation` e estados de UI cobrem os casos enum/sealed; classificadores abertos que produzem valor têm fallback explícito, e o `when(path)` de rotas continua deliberadamente para o lookup/fallback desconhecido. `INVALID_UID`/null nunca caem em UID-alvo e as condições sem valor são apenas contabilidade, não uma classificação de autoria. A compilação Android ainda depende de CI por falta de JDK local.
10. A auditoria de linguagem do IPv6 retirou a frase que excluía o jogo sem UID: o log agora descreve apenas perfis de cabeçalho NDP/MLD, explicita origem desconhecida e não infere causalidade com ausência de TCP; ICMPv6 multicast fora desses tipos fica em `MULTICAST_OUTRO`.

## 8. Próxima observação no device — sem alterar rede nem Private DNS

1. Manter Private DNS habilitado e salvar/exportar a sessão anterior antes de começar.
2. Iniciar o roteador e confirmar no log sessão, pacote/UID-alvo, allow-list aceita, interface VPN e rotas efetivamente reportadas por `LinkProperties`.
3. Executar o teste sintético em janela separada do WZM. O resultado prova somente o caminho iniciado pelo launcher.
4. Anotar contadores `TrafficStats` do UID-alvo antes da chamada de lançamento e em amostras posteriores; registrar se API está disponível. Isso inclui helpers do mesmo UID e não identifica processo.
5. Abrir WZM pelo botão do launcher/`PackageManager`; tratar `markWzmStarted` só como referência temporal. Aguardar “Verificando atualizações” e salvar o `.txt` sem limpar a sessão.
6. Para TCP SYN de bounce, a implementação consulta owner UID na tupla do pacote (`origem -> destino`) e registra protocolo/endpoints/resultado; o suporte API para UDP existe, mas o pipeline atual não executa owner lookup genérico para cada UDP/DNS, então esses pacotes continuam sem atribuição UID. `INVALID_UID`/API indisponível permanecem `UNKNOWN`.
7. Só declarar um caminho real **nesta conexão** quando uma sessão não sintética correlacionar o mesmo fluxo/tupla: SYN observado no TUN + owner UID resolvido igual ao UID do pacote-alvo + conexão aceita no listener do túnel. Isso prova UID (pode incluir helper sob o mesmo UID), não PID/processo nem todo o tráfego do jogo. **Só pacote TUN** = origem desconhecida; **só aumento de UID** = tráfego do UID, não processo/caminho; **só loopback** = diagnóstico; **ausência de evento** = ausência observada, não causa.
8. Não mudar rotas, não desligar Private DNS e não tocar em TLS/pinning. Não adicionar endpoint nem inferir mecanismo DNS sem fluxo atribuído.

## 9. Fontes pesquisadas em 2026-10-04

### Android Developers / API pública

- [VPN guide — per-app VPN, rotas e bypass](https://developer.android.com/develop/connectivity/vpn#per-app) — allow-list e roteamento são controles distintos; rotas filtram destinos.
- [`VpnService.Builder.addAllowedApplication()`](https://developer.android.com/reference/android/net/VpnService.Builder#addAllowedApplication(java.lang.String)) e [`addRoute()`](https://developer.android.com/reference/android/net/VpnService.Builder#addRoute(java.lang.String,int)) — semântica de UID e rotas IPv4/IPv6.
- [VPN guide — Bypass VPN](https://developer.android.com/develop/connectivity/vpn#bypass_vpn) — `allowBypass()`, `bindProcessToNetwork()` e `Network.bindSocket()`.
- [`Network.bindSocket(Socket)`](https://developer.android.com/reference/android/net/Network#bindSocket(java.net.Socket)) — associação explícita de socket a uma rede.
- [`VpnService.protect(Socket)`](https://developer.android.com/reference/android/net/VpnService#protect(java.net.Socket)) — exclusão do socket do túnel VPN que o protege.
- [`ConnectivityManager.getConnectionOwnerUid()`](https://developer.android.com/reference/android/net/ConnectivityManager#getConnectionOwnerUid(int,java.net.InetSocketAddress,java.net.InetSocketAddress)) — API 29+, TCP/UDP, UID e `INVALID_UID`.
- [`Process.myPid()`](https://developer.android.com/reference/android/os/Process#myPid()) — PID do processo chamador.
- [`ActivityManager.getRunningAppProcesses()`](https://developer.android.com/reference/android/app/ActivityManager#getRunningAppProcesses()) — API informativa/debugging, não garantia de inventário cross-app nem tabela socket → PID.
- [`TrafficStats`](https://developer.android.com/reference/android/net/TrafficStats) — estatísticas por UID; disponibilidade dependente da plataforma.
- [`InetAddress` loopback](https://developer.android.com/reference/java/net/InetAddress) — semântica de loopback `127.*.*.*`/`::1`.
- [Android 9 DNS privacy](https://developer.android.com/about/versions/pie/android-9.0-changes-28#dns-privacy) — apps devem respeitar as APIs Private DNS/resolver do sistema.
- [Android 17: Localhost Restriction](https://developer.android.com/work/versions/android-17#localhost-restriction) — restrição cross-profile versionada.
- [Android security enhancements: `/proc/net`](https://source.android.com/docs/security/enhancements) — apps em Android 10+ não acessam diretamente `/proc/net`.
