# M5.3 — O blocker é TLS: análise da pilha, da confiança e do pinning no WZM 3.10

> **Data:** 2026-10-05 · **Modo:** somente análise. **Nada foi alterado, nada foi instalado, nenhum bypass foi tentado.** Nenhuma linha de launcher, nenhum certificado instalado no aparelho, nenhuma alteração no APK ou no `libgame.so`.
> **Pergunta:** qual pilha faz o Meta Fetch, de onde ela tira as CAs, onde valida, existe pinning, e existe caminho legítimo para o WZM aceitar o nosso certificado **sem modificar o APK**.
> **Rótulos:** `VERIFIED` · `REFUTED` · `PROBABLE` · `HYPOTHESIS` · `UNKNOWN` · `[RU]` = relatado pelo usuário em runtime.
> **Veredito M5.3 (`BLOQUEIO_E_CONFIANCA_TLS_NAO_ROTEAMENTO`):** a pilha é `HttpsURLConnection` → `com.android.okhttp` (cópia da plataforma); a confiança vem da **configuração de segurança de rede do Android**, cujo padrão — **`VERIFIED` no AOSP** — é: **somente CAs do sistema**, com a loja de CAs de usuário incluída **apenas se `targetSdk ≤ 23`**. Um jogo de 2024/2025 tem `targetSdk ≥ 34`, portanto **a expectativa forte é que CA de usuário não seja aceita** — mas o valor exato para o WZM 3.10 depende de dois fatos do APK que ainda não temos (`targetSdk` e `res/xml/network_security_config.xml`). **O redirecionamento está provado e funcionando; o que falta é confiança, não roteamento.**

O alerta TLS é do **cliente**, recebido **no nosso listener**. Isso prova que ele chegou, recebeu nosso certificado e o recusou. **Não é** falha de DNS, rota, TUN, bounce, porta ou listener.

## 1. Qual pilha faz o `cdni.meta` (Q1/Q2)

**`VERIFIED` pelo stack trace:**

```text

```

| Hipótese | Veredito | Por quê |
|---|---|---|
| `HttpsURLConnection` (API `javax.net.ssl`) | **VERIFIED** | `HttpsURLConnectionImpl.connect` e `DelegatingHttpsURLConnection` no trace |
| Implementada por `com.android.okhttp` (cópia da plataforma) | **VERIFIED** | todos os frames internos são `com.android.okhttp.internal.*` |
| OkHttp empacotado no app (`okhttp3.*`) | **REFUTED** para esta requisição | nenhum `okhttp3.*` no trace; seria `okhttp3.internal.connection.*` |
| libcurl / nativo (`libgame.so`) | **REFUTED** para esta requisição | o `.so` não tem `java/net`, `android/net`, `okhttp`, `cronet`; o nativo usa libcurl para **outras** URLs (`environment.config`, manifests, shards), e a URL do `cdni.meta` **sai** do nativo para Java pelo getter JNI `0x25dc900` (M4.6) |

Consequência importante: por ser a pilha **da plataforma**, a decisão de confiança segue as regras do Android — inclusive a *Network Security Configuration* — e não uma configuração própria de uma biblioteca empacotada.

## 2. De onde essa pilha obtém as CAs (Q3)

Cadeia **verificada no AOSP** (`android.security.net.config`):

| Passo | Código-fonte | O que faz |
|---|---|---|
| 1 | `ManifestConfigSource.getConfigSource()` | se `ApplicationInfo.networkSecurityConfigRes == 0` → usa o **padrão da plataforma**; senão, usa o XML declarado |
| 2 | `ManifestConfigSource.DefaultConfigSource` | chama `NetworkSecurityConfig.getDefaultBuilder(info)` |
| 3 | `NetworkSecurityConfig.getDefaultBuilder(ApplicationInfo)` | adiciona sempre `SystemCertificateSource`; adiciona `UserCertificateSource` **somente se** `info.targetSdkVersion <= Build.VERSION_CODES.M` (23) **e** o app não for privilegiado |
| 4 | `NetworkSecurityConfig.getTrustAnchors()` | conjunto final de âncoras usado na validação |
| 5 | `NetworkSecurityTrustManager` (via `getTrustManager()`) | `checkServerTrusted` com essas âncoras; o motor TLS é o **Conscrypt** |

Trecho decisivo do AOSP (`NetworkSecurityConfig.java`, branch `main`), **VERIFIED**:

```java
// Applications targeting N and above must opt in into trusting the user added certificate
// store.
if (info.targetSdkVersion <= Build.VERSION_CODES.M && !info.isPrivilegedApp()) {
    // User certificate store, does not bypass static pins. CT is disabled.
    builder.addCertificatesEntryRef(
            new CertificatesEntryRef(UserCertificateSource.getInstance(), false, true));
}
```

E a documentação oficial confirma o mesmo comportamento por outras palavras [4](https://developer.android.com/privacy-and-security/security-config).

**Veredito para Q3 (trust store usado pelo Meta Fetch):** mecanismo **VERIFIED** (padrão da plataforma = CAs do sistema; CAs de usuário só se `targetSdk ≤ 23` ou se o XML optar); **o conjunto efetivo de âncoras do WZM 3.10 é `UNKNOWN`**, porque depende de:
1. `targetSdkVersion` do APK;
2. existência e conteúdo de `res/xml/network_security_config.xml`;
3. o app não instalar um `SSLSocketFactory`/`TrustManager` próprio via `HttpsURLConnection.setDefaultSSLSocketFactory(...)` — possibilidade real, documentada [3](https://developer.android.com/privacy-and-security/security-ssl), e que só o DEX responde.

## 3. Onde ocorre a validação do certificado (Q4)

**VERIFIED** — dentro do processo do WZM, durante `startHandshake()`, **antes** de qualquer byte HTTP:

```
MetaFetchTask.connect()
  └─ Conscrypt (SSLEngine/SSLSocket da plataforma)
       └─ TrustManager padrão → NetworkSecurityTrustManager.checkServerTrusted(chain, authType)
            ├─ âncoras = NetworkSecurityConfig.getTrustAnchors()   (sistema [+ usuário se permitido])
            ├─ pinning  = NetworkSecurityConfig.getPins()          (se o XML declarar)
            └─ hostname = verificação de hostname da plataforma     (nosso SAN cobre o host)
       └─ falha → alerta TLS 46 (certificate_unknown) → SSLHandshakeException
```

Do nosso lado, a mesma fronteira: `LocalHttpsServer.handle()` chama `sslSocket.startHandshake()` e só depois `TcpRelay.serve()` — por isso **nenhum path é registrado**. O alerta `certificate_unknown` é genérico: ele **não distingue** “âncora não confiável” de “falha de pinning” — ambos produzem exatamente o que você observou.

| Tipo | Onde viveria | Evidência no WZM |
|---|---|---|

**Veredito Q5: `UNKNOWN`.** O alerta observado é compatível com “âncora não confiável” (mais provável) e com “pinning” (menos provável, mas não descartado). Sem o DEX/XML não dá para afirmar nem refutar.

## 5. Existe config no APK que permita confiar em CA de usuário sem modificá-lo? (Q6)

A regra é do **APK**, não de nós. Caminhos possíveis:

| Caminho | Exige | Situação |
|---|---|---|
| `<base-config>` ou `<domain-config>` com `<certificates src="user" />` | o APK já declarar | `UNKNOWN` — decide tudo |
| `<debug-overrides>` com CA de usuário | **`android:debuggable="true"`** no manifesto | improvável em build de produção (`HYPOTHESIS` de que não) |
| `targetSdk ≤ 23` | — | praticamente impossível para um jogo de 2024/2025 (Play exige ≥ 34); o `default` do AOSP só confia em CAs de usuário nesse caso |
| app com `TrustManager` próprio que já confie em algo extra | DEX | `UNKNOWN` |

**Veredito Q6: `UNKNOWN`** (a regra que decide é `VERIFIED`). Se o APK **não** tiver opt-in, então, para qualquer `targetSdk ≥ 24`, a resposta é **`REFUTED` por construção da plataforma**.

## 6. O nosso certificado pode ser aceito legitimamente sem modificar o APK? (Q7)

Nosso material (`scripts/generate-local-cdni-cert.sh`, `VERIFIED`): CA descartável nossa + leaf `CN=prod.cdni.callofduty.com`, SANs `DNS:prod.cdni.callofduty.com, DNS:*.cdni.callofduty.com, DNS:cdni.callofduty.com`. **Nome e SANs estão corretos; o emissor, não.** “Legitimidade” aqui é unicamente a política de confiança do cliente.

| Caminho | Modifica o APK? | Situação |
|---|---|---|
| App já confia em CAs de usuário → instalar a nossa como **credencial de usuário** | **Não** | `UNKNOWN` → é exatamente a pergunta do Q6 |
| Nossa CA na **loja de sistema** (`/system/etc/security/cacerts`) | Não (mas altera o dispositivo, exige root) | proibido por você; e no **Android 14+** isso ficou bem mais difícil — as CAs passaram a ser lidas de `/apex/com.android.conscrypt/cacerts`, com relatos de que nem root resolve de forma simples [5](https://httptoolkit.com/blog/android-14-breaks-system-certificate-installation/) |
| Certificado emitido por uma CA pública real para `prod.cdni.callofduty.com` | Não | **impossível/ilegítimo**: não somos donos do domínio e nenhuma CA pública emite para ele sem controle do domínio |
| Modificar o APK (NSC, repack) | **Sim** | proibido por você |
| Hook em runtime (Frida/Xposed/`TrustManager` falso) | Não altera o arquivo, mas é bypass | proibido por você — e é bypass, não caminho legítimo |

**Veredito Q7: `UNKNOWN`**, com condição explícita: **se** `targetSdk ≥ 24` **e** não houver opt-in por CA de usuário (o cenário esperado), então **não existe caminho legítimo sem modificar o APK ou a loja de sistema do dispositivo**, e a resposta vira **`REFUTED`**.

## 8. Como fechar as três lacunas (sem uploads grandes)

1. **`targetSdkVersion` — custo zero, pelo adb:**
   ```bash
   adb shell dumpsys package com.activision.callofduty.warzone | grep -iE "targetSdk|versionCode|flags|debuggable"
   adb shell pm dump com.activision.callofduty.warzone | grep -iE "targetSdk|flags"
   ```
   `targetSdk=34` (ou ≥ 24) fecha o destino da regra do AOSP: **CA de usuário não entra por padrão**.
2. **Existência de `network-security-config`:** `aapt2 dump xmltree base.apk AndroidManifest.xml | grep -i networkSecurityConfig` e `unzip -l base.apk | grep -i "res/xml"`. Se não houver, a regra do AOSP se aplica integralmente.
3. **Teste comportamental (decisão sua, não fiz):** instalar a nossa CA como **credencial de usuário** (Ajustes → instalar certificado; reversível, não altera o APK, não é bypass de pinning) e repetir o teste.
   * se o alerta **continuar idêntico** → CAs de usuário não são confiadas pelo WZM (**conclusivo**);
   * se o alerta **mudar** (p. ex. virar erro de hostname, de pinning ou conexão aceita) → há opt-in, e o caminho legítimo existe.
4. **Pinning (DEX):** `dex-scan.py --dex classes*.dex --search CertificatePinner TrustManager setDefaultSSLSocketFactory X509TrustManager`.

## 10. Conclusão

**O blocker é a confiança TLS — não TUN, não DNS, não roteamento.** O redirecionamento está provado até a porta do nosso listener com o UID do WZM confirmado; o que o cliente recusa é a **cadeia** do nosso certificado, conforme a regra da plataforma (`VERIFIED` no AOSP): apps com `targetSdk ≥ 24` confiam **somente nas CAs do sistema** salvo opt-in explícito no APK.

Se o WZM 3.10 tiver `targetSdk ≥ 24` e nenhum opt-in por CAs de usuário — o esperado —, então **não existe caminho legítimo para o cliente aceitar o nosso certificado sem modificar o APK ou a loja de sistema do dispositivo**, e a investigação do DBDM Offline (M5.1) passa a ser a pergunta central: como o launcher deles resolve exatamente este ponto com o cliente oficial intocado.
