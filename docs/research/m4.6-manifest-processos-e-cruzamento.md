## 2. A cadeia JNI do `cdni.meta` (VERIFIED)

### 2.1 O único consumidor da URL

A URL completa existe **uma vez** no binário, em `0x4e45b8`:

```text
"https://prod.cdni.callofduty.com/wzm/shard_cdn/android/_manifest/cdni.meta"
```

Varredura exaustiva:

* pares `ADRP+ADD` cujo alvo cai em `[0x4e45b8, 0x4e4601]`: **2**; só **1** aponta para o início exato da string — `0x25dc908`. (O outro, `0x367be68`, é emparelhamento espúrio: o primeiro `ADD` depois do `ADRP` é `add x2, x20, #0x5e8`, e o literal real daquela instrução é `emailVerified`.)
* ponteiros crus de 8 bytes para `0x4e45b8` (ou para qualquer byte da string) no arquivo inteiro: **0**.
* não existe literal separado `https://prod.cdni.callofduty.com/wzm` nem `prod.cdni.callofduty.com/wzm` — as únicas strings `prod.cdni…` são as §4.1.

O consumidor é um método JNI de **20 bytes**, registrado em `JNI_OnLoad`:

```text
0x25dc900  ldr  x8, [x0]                ; JNIEnv*
0x25dc904  adrp x1, #0x4e4000
0x25dc908  add  x1, x1, #0x5b8          ; → URL do cdni.meta
0x25dc90c  ldr  x2, [x8, #0x538]        ; slot 167 = NewStringUTF
0x25dc910  br   x2
```

* `0x538 = 167 × 8` → `NewStringUTF` (VERIFIED).
* O endereço do stub é referenciado em `0x25e0fe8`, **dentro** do intervalo de `JNI_OnLoad` (VERIFIED), no mesmo padrão de tabela construída em runtime já visto no 3.3.4.

**Conclusão (VERIFIED):** o binário **expõe a URL do `cdni.meta` para Java**. É a única forma, visível estaticamente, de essa URL chegar a algum emissor de requisição.

1. **A URL/base não vem de um literal**: vem de um método virtual do objeto global `0x6c142d0`, com argumento `2` (VERIFIED). 3. O mesmo objeto global `0x6c142d0` aparece já no **estado 0** do controlador (`0x15a15d8`), ao lado de `mov w9, #0x1ac0` — ele é o gerente do CDNI (PROBABLE).

## 7. Processos — o que pode e o que não pode ser afirmado

* **Insumo indisponível:** não há `AndroidManifest.xml` do build 3.10.0.19854920. A cópia existente (30.080 B) é do APK **3.3.4.17654269** e, portanto, **não** descreve o binário analisado aqui. Logo, se o pedido sair do nativo, sai do processo que carregou a lib — mas **qual** é esse processo, e se existe outro, depende do manifesto do 3.10.0 → `UNKNOWN`.
* **Sem indício de motor alternativo no binário:** 0 ocorrências de `chromium`, `play.core`, `AssetPack`/`assetpack` (VERIFIED). Há strings de WebView do sistema (`webview_open` `0x4a6117`, `WebViewClosed` `0x4ac390`, `WebView System heartbeat timeout` `0x4b86d8`) — o WebView do sistema, quando usado, roda em processo isolado do **provedor** do WebView, não declarado no manifesto do app (HYPOTHESIS, fora do alcance desta leitura).

Leitura combinada (`PROBABLE`):

1. O launcher serviu o `cdni.meta` **ao processo do WZM**; não houve pedido subsequente.
2. Neste build, a URL é **entregue a Java** pelo nativo (§2.1) — portanto o pedido seguinte, se existir, é emitido por código **Java/Kotlin do app**, que não é visível neste artefato. A ausência de tráfego é compatível com uma parada **antes** da criação do socket, em código que só poderíamos ver com o DEX/APK do 3.10.0.
3. Alternativa nativa: se o caminho nativo for o emissor, ele aborta na guarda da URL vazia (`0x15a4e68`) ou nos portões do estado 0 (§5) — de qualquer forma **antes** de `libcurl`, o que explica `tunTcpSyn=0` sem nenhum erro de TLS/DNS/endpoint.

Nenhuma das duas hipóteses é decidível só com o `.so` (`UNKNOWN`). Ambas, porém, afastam a explicação “o pedido saiu e foi bloqueado na rede” — o que é consistente com o usuário ter encerrado a linha de mudanças em `cdni.meta`/TLS.

## 9. Respostas finais

**A) Qual processo parece fazer o primeiro pedido?**
Resposta em duas camadas:
* **Camada verificável (`VERIFIED`/`PROBABLE`):** o pedido é montado **dentro do processo que carregou este `libgame.so`** — a cadeia CDNI → `bdHTTP` (`0x369xxxx`) → libcurl 8.4.0 estático → socket é inteiramente deste binário.
* **Camada do `cdni.meta` (`PROBABLE`):** como a URL do `cdni.meta` tem **um único consumidor**, o getter JNI de `0x25dc900`, e os templates nativos (§3.4) cobrem outros paths, **o primeiro pedido do fluxo tende a ser emitido por código Java do app**, com a URL vinda desse getter — **no processo único do app** (`com.activision.callofduty.warzone`), não em processo auxiliar demonstrado.
* **Sem manifesto do 3.10.0, “qual processo” (uid/pid) permanece `UNKNOWN`.**

**B) Qual função/portão bloqueia ou antecede o pedido?**
1. `0x11cdea4` — fence de pré-login (literal `"disabled"`, `isPreloginFencePassed`) — `PROBABLE`.
2. Estado 0 do controlador (`0x15a158c`): objeto/flags globais — `PROBABLE`.
3. `0x15a4e68` — **guarda de URL vazia**: sai sem criar a requisição — `VERIFIED` o código.
4. `0x1dc5200` (`CDNI_SetAllowCellularDownload`) — política de celular — `PROBABLE`.
5. `0x25f6d80` — leitura de `cdni_httpServer` — `VERIFIED` o código, `UNKNOWN` o efeito.
6. `0x1bc05f0` (`isWifiConnected`) + stubs `GetStringUTFChars` (§2.2) — estado de rede/config empurrado por Java — `PROBABLE`.
**Nenhum** desses portões depende de TLS, DNS, TUN ou do endpoint — o que é coerente com `tunTcpSyn=0`.

**C) Existe processo auxiliar?**
`UNKNOWN` para o 3.10.0 (sem manifesto). Contexto histórico do APK 3.3.4 (não usado como evidência aqui): zero `android:process`/`isolatedProcess`. Dentro do `.so` não há indício de transporte alternativo (sem `chromium`/`play.core`/`AssetPack`).

**D) Próximo experimento mínimo para confirmar (sem tocar em TLS/TUN/DNS/endpoint/dvars/binário):**
* **D1 — observação passiva por `logcat`** (recomendado): filtrar as strings que o próprio binário publica — `CDNIStateString`, `CDNIStateEnum`, `CDNIErrorCode`, `CacheValidation`, `CDNI_TaskFuncCacheValidation`, `bdHTTPWorker(CURL)`, `isCDNIFinished`, `isPreloginFencePassed`, `FetchingManifest` — durante o travamento. Se nenhuma aparecer, a parada é **antes** do controlador (Java/fence); se aparecerem e pararem em determinado estado, o portão é aquele estado. Custo zero de código funcional: apenas observação.
* **D2 — identidade do APK instalado**: `pm dump com.activision.callofduty.warzone | grep version` (ou `dumpsys package`) para registrar `versionName`/`versionCode`/`splitName`, fechando o único ponto de escopo que resta (manifesto do 3.10.0).
* **D3 — (só se D1/D2 apontarem para Java)** obter o `AndroidManifest.xml` e os DEX do build 3.10.0 para leitura estática, **sem** extrair/modificar o APK do jogo em produção.
Nenhuma dessas ações altera código funcional, TLS/pinning, VPN/TUN, DNS ou endpoints.

## 10. Limites desta análise

* Um único artefato (`.so`), sem DEX, sem manifesto do build instalado, sem execução.
* O significado de **flags globais** (`0x6c15d90`, `0x6c15990`, `0x69df5f0`, …), dos **cinco valores string empurrados por Java** e do **efeito** de `cdni_httpServer` é `UNKNOWN`; nada foi inferido além do que o código mostra.
* Consultas por **hash de 64 bits** (`0x143bef8`, `0x143de14`) não são resolvíveis estaticamente → partes do fluxo de dvars ficam fora do alcance.
* Limites de função por `.eh_frame_hdr` e xrefs por `ADRP+ADD`: emparelhamentos espúrios existem (um foi identificado em §2.1) e funções sem FDE ficam invisíveis.
* Nenhuma conclusão desta revisão usa o `libgame.so` 3.3.4.17654269; os documentos [M4.3](m4.3-libgame-static-analysis.md) e [M4.5](m4.5-cadeia-estatica-ate-connect.md) permanecem como metodologia/narrativa, com **endereços inválidos para este binário**.
